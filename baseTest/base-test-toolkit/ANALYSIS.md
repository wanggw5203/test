# 自动化测试基础框架设计分析

## 1. 分析对象与结论

分析对象是一个 520,457 字节、Java 21 构建的测试基础库 JAR。制品包含 245 个 class，除了配置加载，还聚合了数据驱动、TestNG 生命周期、账号上下文、Mock、远程配置、测试报告、覆盖率、服务发现、任务调度和数据工厂等能力。

它的本质不是“工具类集合”，而是一个测试运行时：

```text
测试代码
  -> TestNG 生命周期和注解
  -> 数据驱动、身份上下文、Mock 上下文
  -> HTTP/RPC/数据准备调用
  -> 断言、日志和覆盖率
  -> 本地报告及远程结果平台
```

原框架的优点是接入成本低、平台能力集中；主要代价是静态全局状态较多，测试执行与组织内部基础设施紧密耦合，脱离原环境后难以独立运行。

## 2. 制品结构

按 class 数量统计，主体分布如下：

- DTO：65 个。
- Mock：36 个。
- 数据驱动：24 个。
- 服务治理与环境发现：22 个。
- 请求模型：12 个。
- TestNG：9 个。
- Feign 客户端：9 个。
- 环境枚举：8 个。
- 通用工具：7 个。
- 账号上下文：6 个。
- 加密配置：4 个。
- 日志：4 个。
- 其余为配置入口、覆盖率、分页模型、注解处理器和自动配置。

这说明框架的重心依次是：平台模型、Mock、数据驱动、环境连接和执行上报。

## 3. 总体架构

### 3.1 启动层

Spring 自动配置负责读取环境、分支、泳道、区域和项目参数，并初始化远程客户端、对象映射器、线程池、账号配置和中间件配置。

TestNG 通过服务发现自动加载监听器。测试开始前注册待执行用例；单例开始时绑定用例、账号和 Mock 上下文；结束时上报结果、日志和覆盖率；套件结束后发送运行结束事件。

### 3.2 上下文层

框架主要使用线程本地变量保存：

- 当前测试账号。
- 当前 Mock 场景。
- 当前用例结果标识。
- 数据准备返回值。
- 方法返回值和命名返回值。

这种设计支持并发执行，但所有入口都必须在测试结束时清理，否则线程池复用时可能发生上下文污染。

### 3.3 平台适配层

原框架直接持有多个静态远程客户端，分别处理：

- 用例注册和结果上报。
- 加密配置获取。
- 账号认证。
- Mock 场景管理。
- 调用日志保存。
- 定时任务触发和日志查询。
- 覆盖率制品下载。
- 服务实例和环境信息查询。

通用化版本将这些客户端改为明确的接口，由使用方注入适配器。

## 4. 完整能力分析

### 4.1 测试基类

原基类继承 Spring TestNG 基类并接管测试方法执行。它使测试能够直接使用 Spring 容器、自动配置和监听器。

通用版 `BaseTest` 保留用例上下文绑定、环境读取和执行后清理，不强制依赖业务 Spring 容器。

### 4.2 多格式配置加载

原框架支持 YAML、JSON、JSON5、CSV、POM 属性及部分文件上传资源。对象映射器包含：

- lowerCamel 和 snake_case 命名策略。
- 是否保留 null。
- YAML 映射。
- 严格基础类型检查。

通用版由 `ConfigLoader` 和 `StrictTypeModule` 提供 YAML、JSON、JSON5 及严格类型反序列化。

### 4.3 环境解析

原框架按配置文件、JVM 参数和静态配置解析环境，并进一步计算分支、泳道和区域。它包含大量组织特有环境枚举。

通用版只保留 `TestEnvironment`：

- `test.env` / `TEST_ENV` 指定环境。
- `test.attr.*` / `TEST_ATTR_*` 传递任意环境属性。
- 不内置任何公司环境名称。

### 4.4 中间件连接配置

原框架可获取数据库、缓存、搜索、消息队列、对象存储、分析数据库、RPC 和配置中心等连接信息，并支持：

- 远程加密配置。
- 本地缓存兜底。
- 本地配置覆盖远程配置。
- 按名称和类型检索连接。

通用版使用 `ConnectionSpec` 和 `ConfigCatalog` 表达统一连接目录。敏感属性不会出现在 `toString()` 中。

### 4.5 加密配置

原框架包含动态密钥、公钥注册、配置类型扫描、远程密文获取和本地解密流程。

这部分依赖专用密钥服务，通用版不复制算法和协议。应由使用方实现配置源，在边界内返回已经授权的 `ConnectionSpec`。

### 4.6 YAML 数据驱动

原框架的用例模型包括：

- `testDataSuite` 根节点。
- `description`、`cases`、`debugCases`、统一参数模式。
- 用例 `name`、`enabled`、`thought`、`mockId`、`users`。
- `request`、`expect` 文件列表。
- `extraParams` 扩展参数。

加载器按测试方法的泛型参数顺序读取请求和预期文件，并能根据环境、命名策略和参数名做转换。

通用版保留稳定的数据文档结构、强类型参数装配、禁用用例和调试用例筛选。

### 4.7 数据准备桥接

原框架使用 `@DataBuilder`、Java 注解处理器和 TestNG 套件修改器，把普通数据构造方法生成 TestNG 适配类，并允许：

- 数据构造方法有返回值。
- 将返回值传递给后续数据工厂。
- 兼容旧的统一参数模式。
- 使用可选参数默认值。

通用版提供中性 `@DataBuilder` 和 `DataBuilderProcessor`，同时以 `DataFactory` SPI 表达外部造数能力。

### 4.8 参数转换与返回值传递

原框架支持简单值、泛型对象、列表、Map、环境占位符和命名返回值转换，并维护方法级返回值列表。

通用版保留 `TypeConverter`、`ReturnValueContext` 和 `CaseContext`。跨用例共享仍应通过显式数据准备器完成，避免依赖执行顺序。

### 4.9 JSON 断言

原框架包含严格和宽松两种比较模式：

- 类型差异。
- 值差异。
- 缺失字段和多余字段。
- 数组长度和顺序差异。
- JSONPath 忽略与通配符匹配。
- 宽松模式允许实际结果包含额外字段。

通用版 `JsonDiff` 返回结构化 `Difference`，支持严格、宽松和忽略路径。

### 4.10 身份与账号池

原框架支持多个业务端账号类型、登录取令牌、随机选择空闲账号、账号锁和嵌套线程上下文，并通过注解在测试开始时自动切换用户。

通用版提供：

- `UserIdentity`：中性身份模型，令牌输出自动脱敏。
- `IdentityProvider`：认证或账号池接口。
- `InMemoryIdentityProvider`：本地互斥账号池。
- `IdentityContext`：可嵌套、线程隔离、自动关闭。
- `@UseIdentity`：TestNG 自动绑定身份配置。

### 4.11 Mock DSL

原框架支持 HTTP、RPC 和本地调用 Mock，具备：

- CASE 和 THREAD 隔离模式。
- 动态请求头隔离。
- 请求参数、请求体、响应和调用次数配置。
- 远程代理及本地代理启动/停止。
- 场景开启、关闭和批量配置。
- 请求记录、消息记录和 Mock 断言。
- 守卫条件和直接调用模式。

通用版用 `MockEngine`、`MockScenario`、`MockRule`、`MockSession` 表达完整生命周期。`InMemoryMockEngine` 用于学习和单元测试；真正拦截 HTTP/RPC 需要实现对应适配器。

### 4.12 TestNG 生命周期

原监听器在执行前展开数据驱动用例并预注册；执行中动态替换用例描述；执行后异步上报结果；套件结束时等待线程池、刷新覆盖率并发送结束通知。

通用版 `PortableTestNgListener` 自动处理：

- 测试开始时间。
- 身份上下文。
- 数据用例中的 Mock 场景。
- 成功、失败、跳过结果。
- Mock 和身份清理。
- 运行汇总。

### 4.13 结果发布与报告

原框架同时支持远程结果平台和本地 HTML 报告。报告包含类、方法、描述、开始时间、耗时、状态和日志。

通用版以 `ResultPublisher` 表达结果出口，并提供 `InMemoryResultPublisher`。文件、HTML、数据库或远程平台发布器可独立实现。

### 4.14 调用日志

原框架通过日志 Appender 收集普通日志、HTTP 请求和异常信息，并可批量保存调用日志。

通用版使用 `InvocationRecord` 和 `InvocationLogSink`。调用封装层负责在请求完成后写入，不依赖具体日志平台。

### 4.15 用例覆盖率

原框架按用例结果 ID 调度覆盖率抓取，支持批量、异步、套件结束前刷新和下载制品。

通用版使用 `CoverageCollector`、`CoverageRequest` 和 `CoverageArtifact`。默认实现不产生覆盖率，接入 JaCoCo 或远程覆盖率系统时实现该接口。

### 4.16 定时任务

原框架可按环境、应用、执行器和参数触发任务，并查询任务日志。

通用版使用 `JobService`、`JobRequest` 和 `JobExecution`，不绑定具体调度产品。

### 4.17 服务发现与环境路由

原框架可按服务、环境、泳道和区域查询实例，过滤健康实例并缓存服务地址。

通用版使用 `ServiceDiscovery`、`ServiceQuery` 和 `ServiceInstance`。可对接 Kubernetes、Consul、Eureka 或静态配置。

### 4.18 数据工厂

原框架能将数据构造输入和调用日志发送到远程数据工厂，并接收运行时结果。

通用版使用 `DataFactory` 和 `DataPreparationRequest`。数据工厂输出为命名 Map，可写入 `ReturnValueContext` 或脚手架的 `__DATA_REF`。

### 4.19 分页与通用响应模型

原框架包含分页请求、Spring Page 实现、分页元数据和平台响应包装。

通用版保留最小 `PageRequest`、`PageResult`，不保留组织特有错误码包装。

### 4.20 通用辅助能力

原框架还包含重试、文件读取、CSV、Multipart、日期、UUID、MD5、Token 包装、curl 日志、Apollo 读取和 Host 模板等工具。

通用化原则是按职责放入请求客户端、配置源或测试夹具，不继续扩张静态 `Util` 类。

## 5. 设计优点

1. 测试编写者只需关注业务用例，环境和平台能力由框架处理。
2. YAML 与 JSON5 分离请求和预期，适合批量生成和评审。
3. 数据构造、Mock、账号和结果上报形成完整执行链。
4. TestNG 监听器统一处理并发、日志、结果和清理。
5. 严格类型比较可以发现接口字段类型回归。

## 6. 设计风险

1. **静态状态较多**：客户端、线程池、环境和缓存均有静态入口，测试隔离依赖严格清理。
2. **职责集中**：一个配置模块同时承担配置、认证、执行、Mock、报告和平台上报。
3. **平台耦合**：环境枚举、域名、认证和服务治理逻辑写入基础库。
4. **隐藏副作用**：ServiceLoader 自动监听会在引入依赖后改变 TestNG 行为。
5. **失败边界模糊**：部分远程失败采用日志后继续，可能让配置问题延迟到业务调用阶段。
6. **敏感信息风险**：账号和连接模型若直接生成 `toString()`，可能被日志打印。
7. **Java 版本约束**：原注解处理器固定 Java 21，限制旧项目接入。

## 7. 通用化后的架构

```text
BaseTest / PortableTestNgListener
  |
  +-- DataDriveUtil / JsonDiff / StrictTypeModule
  +-- IdentityProvider / IdentityContext
  +-- MockEngine / MockSession
  +-- DataFactory
  +-- ResultPublisher / InvocationLogSink
  +-- CoverageCollector
  +-- JobService
  +-- ServiceDiscovery
  +-- ConfigCatalog
```

所有外部能力从 `AutomationRuntime` 显式组合。默认本地运行不会访问网络、读取账号或发送任何结果。

## 8. 去敏策略

- Maven 坐标改为 `io.testkit:base-test-toolkit`。
- Java 包统一为 `io.testkit.basetest`。
- 删除内部域名、环境枚举、组织缩写、员工账号和认证协议。
- 业务端账号改为 profile，例如 `reviewer`、`operator`。
- 服务治理中的泳道保留为普通 `lane` 属性，不携带内部路由规则。
- 私有平台客户端全部替换为 SPI。
- 所有包含令牌或连接属性的模型禁止直接输出明文。

## 9. 实现边界

当前通用 JAR 已真实实现：配置加载、严格类型、数据驱动、类型转换、JSON 比较、身份上下文、本地账号池、本地 Mock 场景、测试结果内存发布、TestNG 生命周期、分页模型和能力组合入口。

当前通用 JAR 只提供接口：远程认证、真实 HTTP/RPC Mock、远程配置解密、结果平台、调用日志平台、覆盖率平台、任务调度、服务发现和远程数据工厂。这些能力必须由使用方实现适配器后才会连接真实环境。
