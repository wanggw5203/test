# 企业自动化框架技术补齐路线图

资料核查日期：2026-10-15。本路线图结合当前代码和官方技术文档给出优先级建议；以下“拟补齐”和“验收条件”均是后续工作，不能作为已经实现或通过验收的能力。当前本机未发现 Docker 命令，因此没有执行真实容器 Kafka/数据库集成验收；Docker 命令不可用也不能推断远端一定不存在可用容器平台。

100 人团队首先需要稳定的职责分工、资源配额、可复现验证和发布证据。新技术只有解决明确缺口并满足验收条件后，才进入默认执行链路；不因接入一个依赖就宣称框架已经具备完整平台能力。

## 优先级和现状

| 优先级 | 补齐方向 | 当前基础 | 完成标准的核心 |
| --- | --- | --- | --- |
| P0 | Testcontainers 真实 Kafka、生产同型数据库隔离集成 | Kafka Mock 客户端、H2 和本地协议测试 | 真实容器、跨进程隔离、异常路径和清理均有 CI 证据 |
| P1 | OpenTelemetry 与 W3C 上下文传播 | `TraceContext` 关联 runId/caseId 并显式跨 SDK 线程传播 | HTTP/消息/SDK 链路可关联，采集故障不掩盖业务结果 |
| P1 | Pact 消费者契约和消息 Schema 演进 | JSON 断言、关联消息观察和协议适配 | 消费者及提供者双向验证，破坏性变更在发布前被阻断 |
| P1 | SCA、SBOM、可信签名和 SLSA 构建来源 | CycloneDX SBOM、源码与制品哈希证据 | 扫描策略有效，来源可验证，制品篡改和未知签名被拒绝 |
| P2 | JDK 21+ 虚拟线程适配 | Java 17 编译基线、有界 SDK 执行和显式上下文 | 可选适配、有配额和背压，性能收益由相同负载证明 |
| P2 | AI 辅助用例设计和失败归因 | 确定性测试、元数据和结构化报告 | 人工审核、固定业务判定标准、效果评估和完整审计 |

## P0：真实依赖与隔离集成

**现状。** 当前本地测试能验证客户端契约和框架逻辑，不能替代真实 Kafka broker、生产同型数据库的驱动/事务/时钟/锁竞争语义。H2 租约测试通过，不等于任意 MySQL、PostgreSQL 或公司实际数据库均已通过。

**拟补齐。** 建立独立的容器集成测试入口，由 TestNG 生命周期显式创建和关闭容器，选择与公司环境一致的 Kafka 和数据库版本，并固定镜像版本及摘要。Topic、consumer group、数据库/schema 和业务数据按 run/worker 隔离。CI 禁用实验性的可复用容器，避免残留数据影响后续运行；官方明确说明该特性不适用于 CI。Kafka 容器应选择官方当前推荐的 `org.testcontainers.kafka` 包入口，避免复制已弃用的示例类名。[Kafka 容器模块](https://java.testcontainers.org/modules/kafka/)、[可复用容器限制](https://java.testcontainers.org/features/reuse/)

**验收条件。**

1. 有容器运行时的专用 CI 节点执行真实生产/消费、消息关联、消费超时、offset 提交和失败后的重试路径；缺运行时必须明确阻断该集成入口，不能静默跳过后报绿。
2. 使用生产同型数据库验证租约竞争、续期、过期接管、旧 owner 不能释放新 owner，以及迁移脚本、连接池和时间戳语义；至少增加两个独立 JVM 的竞争证据。
3. 两个并发 run 的 Topic/group/schema 和 fixture 不互相读取或删除；失败/取消后验证容器、连接和测试数据的清理结果。
4. 保存镜像摘要、平台版本、测试结果和必要的脱敏诊断信息。SASL/TLS、真实 XXL-JOB Admin/Executor、Dubbo 注册中心和公司网络权限仍进入 dev/qa 平台验收，不由单节点本地容器结果代替。

建议责任方：框架维护者负责生命周期和隔离，平台团队负责容器节点/镜像准入，业务团队负责生产同型配置和业务断言。

## P1：OpenTelemetry 与 W3C 传播

**现状。** 本框架的 `TraceContext.Trace(runId, caseId)` 是测试运行关联信息，不是 OpenTelemetry SpanContext，也没有提供完整的 traceId/spanId、采样和导出链路。不能把 runId 填入 `traceparent` 后声称兼容 W3C。

**拟补齐。** 先验证公司已有 Java agent 能覆盖哪些客户端，再通过可选适配器为用例生命周期和未覆盖的 SDK/任务边界补 span。HTTP 使用标准传播器处理 `traceparent`/`tracestate`；消息头传播及父子 span 或 span link 的选择按消息语义设计。runId/caseId 作为经批准的业务关联属性保留。OpenTelemetry 提供 agent、库及手工插桩等方式，W3C 规定 HTTP 传播格式，两者职责不同。[OpenTelemetry Java 插桩](https://opentelemetry.io/docs/languages/java/instrumentation/)、[W3C Trace Context](https://www.w3.org/TR/trace-context/)

**验收条件。** HTTP → 服务 → 消息 → 消费者的受控演练可在采集端关联；SDK 线程切换和并发用例不串上下文；超时、异常、取消和作用域清理后没有遗留 span。禁用 agent、无采集端和导出超时时，框架行为符合预先定义的策略；不能把采集失败伪装成业务失败，也不能丢弃实际的业务失败。限制属性和 baggage，确认凭证及原始敏感载荷不会进入遥测，并记录基准开销。

建议责任方：可观测平台团队和框架维护者共同制定传播、采样及保留策略。

## P1：消费者契约与消息 Schema 演进

**现状。** JSON 结构断言检查当前结果，不能证明多个独立发布的消费者与提供者版本互相兼容。消息相关测试也不代表已经接入 Pact 或 Schema Registry。

**拟补齐。** 优先选一个跨团队 HTTP 接口和一个重要事件，建立消费者生成契约、提供者验证契约和版本化验证结果的闭环。消息契约检查生产/消费载荷；真实 broker 的投递、重平衡和 offset 行为仍由集成测试覆盖。Schema Registry 的兼容策略按消费升级顺序及历史消息回放要求选择；例如需要读取全部历史 schema 时，应评估 transitive 检查，不能仅接受默认的相邻版本检查。[Pact 工作原理及消息契约](https://docs.pact.io/getting_started/how_pact_works)、[Schema 演进和兼容规则](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html)

**验收条件。** 在消费者/提供者的实际代码上验证契约；新增可选字段可以通过，删除必需字段或修改不兼容类型会阻断发布。至少覆盖旧消费者/新提供者、新消费者/旧事件及多版本历史回放的实际支持范围。发布决策绑定契约版本、应用版本和目标环境；契约存储服务不可用时有明确失败策略，不能沿用不明版本的旧结果。

建议责任方：领域服务 owner 维护契约含义，平台团队维护契约存储和发布查询，框架提供一致入口与结果归档。

## P1：SCA、SBOM、可信签名和构建来源

**现状。** 根构建已接入固定版本 CycloneDX Maven Plugin 2.9.1，并显式包含 test scope；本轮提供源码指纹、报告/计划/制品/SBOM 哈希的验证证据。SBOM 是依赖清单，哈希证明内容是否变化：二者都不是漏洞扫描，也不能证明签发者可信。目前没有因此获得任何 SLSA 等级或制品签名能力。官方插件版本表中 2.9.x 对应 CycloneDX 1.6；这里记录仓库当前选择，不宣称它是最新版本。[CycloneDX Maven Plugin](https://cyclonedx.github.io/cyclonedx-maven-plugin/)

**拟补齐。** 接入公司批准的 SCA 和许可证策略，记录漏洞数据源更新时间、扫描范围及有时限的豁免；对构建来源证明和发布制品引入受控签名与消费端验签。SLSA v1.1 页面已标为 Retired，当前核查按 v1.2 官方构建来源及验证要求制定实施方案；等级由实际构建平台控制项评估，不能由一份本地 JSON 自行宣告。[SLSA v1.1 状态](https://slsa.dev/spec/v1.1/levels)、[SLSA v1.2 规范](https://slsa.dev/spec/v1.2/)

**验收条件。** 用已知不合规依赖验证扫描门禁会失败；数据源过期、扫描异常和未审批豁免不能报绿。签名绑定具体制品及构建来源，消费端校验受信身份、源码版本、构建入口和摘要；篡改 JAR、伪造来源、未知签名者和过期授权均应被拒绝。构建签名身份与普通业务流水线权限分离，私服发布权限和回滚流程实际演练，验证记录随版本保存。

建议责任方：安全/供应链团队维护策略和签名信任，CI 团队维护构建身份，框架维护者保证依赖和证据完整。

## P2：JDK 21+ 与虚拟线程

**现状。** 当前保持 Java 17 编译基线。使用 JDK 21 运行现有测试，不等于代码已经使用虚拟线程，也不等于所有协议客户端都适合直接替换执行器。

**拟补齐。** 在明确升级策略后，为阻塞 I/O 较多的 SDK 或编排任务提供可选虚拟线程执行器。按服务、账号、连接池和消息端点独立设定并发额度；虚拟线程数量不能成为目标服务的流量许可。Oracle 官方建议每任务一个虚拟线程，并使用专门的并发控制结构限制稀缺资源，而不是池化虚拟线程。[Oracle JDK 21 虚拟线程指南](https://docs.oracle.com/en/java/javase/21/core/virtual-threads.html)

**验收条件。** 在相同数据集和目标容量下比较吞吐、延迟、CPU、内存与排队，只有获得可说明的收益才推广。饱和时有背压或明确拒绝，超时/取消可终止等待，第三方客户端的取消限制被记录；身份、企业上下文和 trace 能正确传播及清理。平台线程模式保留回退，并评估驱动、锁竞争及线程局部缓存带来的兼容影响。不能降低超时、限流和清理要求换取表面并发量。

建议责任方：框架维护者与性能团队共同验证，不直接改动所有团队的默认执行器。

## P2：AI 辅助测试与失败归因

**现状。** 当前没有将模型输出作为断言依据、自动修改断言或自动放行发布的能力。本方向是团队治理建议，不是声称某个模型已经能够可靠替代测试 owner。

**拟补齐。** 先用于依据接口规格提出边界用例、对脱敏失败证据进行聚类和给出排查建议。每项建议附来源、模型/提示版本和输入证据，由 owner 审核。业务正确性仍由需求、契约及固定 oracle（预先确定的业务判定标准）裁决。NIST AI RMF 提供风险管理参考；以下人工审核和禁止自改断言的要求，是本框架建议采用的具体工程控制。[NIST AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework)

**验收条件。** 用预先标注且固定的失败样本评估误归因、漏报和实用性，不以“解释听起来合理”计分；按团队预先约定的门槛审批上线。模型建议可追踪、可拒绝、可回滚，外部输入不能成为自动执行指令。涉及业务断言和 expected 值的变更必须人工评审并保留差异；禁止失败后自动改断言、放宽阈值或删除用例来恢复绿色。敏感数据脱敏与模型访问权限经公司批准，模型故障不影响确定性测试和原始证据保存。

建议责任方：测试平台 owner 组织评估，业务 owner 审核正确性，安全团队管理数据和模型访问。

## 建议推进顺序

先补 P0 真实依赖的可复现 CI 验收，再选择一个领域服务完成三项 P1 的最小闭环。虚拟线程和 AI 先采用小范围可回退试点，不先全团队强制切换。每项完成后更新能力总览、学习路线及验收记录，写明实际版本、执行环境、成功和拒绝场景；未达到本节验收条件的能力继续保留为规划。
