# 订单创建与参数校验需求

本需求用于新建的独立 HTTP 自动化项目验收，不依赖公司服务。接口为本地合成业务服务 POST /demo/orders，运行时由验证程序动态分配回环地址端口。

## 业务场景

用户在确认商品后提交商品编码和数量，服务返回订单编号。参数不合法时不得创建订单。

## 业务规则

- BR-001：输入 sku=SKU-DEMO、quantity=1，返回 HTTP 201，JSON 为 {"code":"OK","orderId":"ORDER-DEMO-001"}。
- BR-002：输入 sku=SKU-DEMO、quantity=0，返回 HTTP 400，JSON 为 {"code":"INVALID_QUANTITY"}。
- BR-003：未传 sku、quantity=1，返回 HTTP 400，JSON 为 {"code":"SKU_REQUIRED"}。

## 验收要求

1. 从该文档生成 TAD、YAML 功能测试用例和接口规格，并保持 BR → caseId → 测试数据追溯。
2. 初始化 HTTP 自动化项目，引入当前 TestNG 框架；main 放初始化、环境加载和接口/造数扩展，test 放测试方法、YAML 和 JSON/JSON5 数据。
3. 实际编译并执行初始化验证和三条接口用例，保存原始结果，不能把生成成功视为执行成功。
4. 将数量为零分支的本地服务故意改错一次，测试应失败；恢复服务后应重新通过。
5. 保存执行反馈；黄金集返回固定内容、真实业务环境未验证、页面未执行等限制必须显式记录。

## 验证边界

当前默认模型使用 order-create-v1 黄金集，因此前三条业务规则刻意与黄金集契约一致，验证的是工具工程链路而非真实模型的分析能力。
额外以“增加 BR-004：数量为负数也拒绝”为变化探针，检查黄金集能否响应需求变化。不得因为固定结果通过结构门禁就宣称已覆盖变化后的需求。

没有真实数据库、注册中心、页面或业务 SDK。本地服务执行成功不代表真实业务系统已经通过测试。
