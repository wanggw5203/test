# 自动化框架与 IDEA 插件：完整使用手册

适用环境：Windows、JDK 21、Maven 3.9+、IDEA、AI Test Flow 1.6.1。本文使用当前仓库提供的本地订单服务，不需要公司环境、数据库或注册中心。

**先记住：启动一次 service，会同时启动 HTTP 和 Dubbo；插件生成文件不等于运行测试；验证 Dubbo 必须真正运行 RPC 用例，不能只看 HTTP 健康检查。**

## 3. 启动本地服务：HTTP 和 Dubbo 一起启动

### 3.1 推荐：双击脚本

进入主目录，双击 start-service.cmd。
脚本会构建 service、后台启动 Java 进程、等待健康检查；不弹出额外的服务控制台。
成功输出应包含：

```text
HTTP: http://127.0.0.1:18081/demo/orders
Dubbo: dubbo://[::1]:20891 ; demo.golden.OrderService#create(java.util.Map)
PID: 某个进程号
```

不要在 IDEA 再点一次 LocalOrderApplication 的 Run。脚本实例和 IDEA 实例不能同时占用相同端口。

### 3.2 PowerShell 启动方式

```powershell
cd E:\AITest\test\validation\local-http-dubbo-flow-20261018
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Start-LocalService.ps1
```

已经构建过、只想快速启动：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Start-LocalService.ps1 -SkipBuild
```

这里只对本次进程使用执行策略参数，不修改系统全局执行策略。脚本识别到自己启动的实例已运行时会返回 Already running，不会重复启动。

### 3.3 检查 HTTP 和 Dubbo 两个端口

```powershell
Invoke-RestMethod http://127.0.0.1:18081/health
Get-NetTCPConnection -State Listen -LocalPort 18081,20891 |
    Select-Object LocalAddress,LocalPort,OwningProcess
```

预期：健康结果 status=UP、faultyZero=false；HTTP 监听 127.0.0.1:18081，Dubbo 监听 ::1:20891，通常是同一个进程号。
runtime/ready.json 保存本次进程及地址，但它可能是旧状态，**文件存在不代表服务还活着**，要结合健康检查和监听端口。

HTTP 健康检查只能证明 HTTP 管理入口可达；真正的 Dubbo 业务验证必须完成第 6 节。

### 3.4 Dubbo 到底怎样启动和配置

不需要单独再启动一个“Dubbo 服务”：LocalOrderApplication 启动时会 export OrderService，同时启动 HTTP server。
提供者是 service/src/main/java/demo/golden/OrderService.java，业务规则是 service/src/main/java/validation/service/OrderRules.java。

| 项目 | 当前值 |
| --- | --- |
| 协议 | Dubbo TCP，不是 HTTP |
| 直连 URL | dubbo://[::1]:20891 |
| interface | demo.golden.OrderService |
| method | create |
| parameterTypes | java.util.Map（一个参数） |
| 返回类型 | java.util.Map |
| group / version | 均为空，消费者必须匹配 |
| registry | N/A，表示本地直连不依赖注册中心 |

::1 是 IPv6 本机回环，不是 0.0.0.0。这里选择它是为了避免 Dubbo 将 127.* 当成自动探测地址后暴露局域网监听。
不要把 dubbo:// 地址粘到浏览器当 HTTP 页面打开；也不要将 RPC 端口写成 HTTP 的 18081。

### 3.5 如果一定要在 IDEA 中启动服务

1. 先用 stop-service.cmd 停止脚本实例。
2. IDEA 打开 service/pom.xml 并导入 Maven。
3. 打开 validation.service.LocalOrderApplication，运行 main。
4. 默认程序参数为空即可使用 18081/20891；建议将 Working directory 设置为本手册主目录，使 runtime 状态文件位置统一。
5. 看见 READY HTTP ... ; RPC ... 后再运行测试。
6. IDEA 启动的进程在 IDEA 中点击 Stop 停止；停止脚本故意不误杀其他启动方式的 Java 进程。

## 4. 先手动验证 HTTP 接口

健康地址可以用浏览器访问；/demo/orders 必须发送 POST，而不是浏览器地址栏的 GET。

```powershell
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:18081/demo/orders -ContentType application/json -Body '{"sku":"SKU-DEMO","quantity":1}'
```

预期业务体：code=OK、orderId=ORDER-DEMO-001，HTTP 状态 201。

测试规则如下，生成的测试会验证状态码和完整业务体：

| 规则 | 请求 | HTTP | Dubbo 业务响应 |
| --- | --- | --- | --- |
| BR-001 | sku=SKU-DEMO，quantity=1 | 201，code=OK、orderId=ORDER-DEMO-001 | 相同业务体 |
| BR-002 | sku=SKU-DEMO，quantity=0 | 400，code=INVALID_QUANTITY | code=INVALID_QUANTITY |
| BR-003 | 只传 quantity=1 | 400，code=SKU_REQUIRED | code=SKU_REQUIRED |

PowerShell 对 HTTP 400 抛出非成功状态异常是正常客户端行为；不代表服务没启动。先跑成功请求确认连通性，反向场景交给自动化断言。

先确认第 3 节服务还在运行，然后执行：


### 6.4 如何证明不是“服务没启动但测试空跑”

至少同时检查：

1. 服务端口 ::1:20891 正在监听。
2. 测试控制台出现 [TESTKIT CALL]，protocol=DUBBO、method=create、目标 dubbo://[::1]:20891。
3. REQUEST 中有 arguments，RESPONSE 中有业务 code，callId 可以配对。
4. 用例断言通过，不是只有编译成功或只有初始化用例通过。
5. 主目录 runtime/service-requests.jsonl 新增 protocol=DUBBO 的记录，时间与本轮测试一致。

runtime 日志是追加写入，旧 DUBBO 记录不能单独证明本轮执行；结合当前时间、报告 runId 和服务存活情况核对。

## 7. 不要混淆几种启动入口

| 入口 | 做什么 | 通过判据 |
| --- | --- | --- |
| service 的 LocalOrderApplication.main | 启动被测 HTTP/Dubbo 服务 | READY、两个端口、健康检查 |
| 测试项目 mvn test | 执行整个模块的测试 | 4 条结果和实际调用日志 |
| GoldenOrderHttpTest / GoldenOrderDubboTest | 仅执行对应 3 条业务测试 | 3 条结果和实际调用日志 |
| 测试项目 AutomationMain | 用 TestNG XML 启动所选测试 | 必须确认 XML 选中了业务测试 |
| 插件“运行完整链路” | 生成项目资产 | 文件和门禁通过，不等于测试已运行 |

特别注意：初始化生成的 src/test/resources/testng.xml 按初始化包扫描，黄金集的 demo.golden 包可能不在扫描范围。**只运行出 1 条初始化测试不能算 HTTP/Dubbo 已验证。**
建议优先 mvn test 或右键具体业务测试类；需要 TestNG XML 时，使用 .api-test-generator/对应 apiCode/testng.xml，它显式列举本次生成的业务测试类。
AutomationMain 需要 test 编译输出和资源，不能只靠 main 的类路径运行。

## 9. 看日志与定位失败

### 9.1 三类输出不要混淆

| 输出 | 路径 | 作用 |
| --- | --- | --- |
| 框架调用日志 | target/logs/api-calls-进程号.jsonl | URL/RPC、入参出参、耗时、异常、callId |
| 测试结果 | target/test-results.jsonl；target/surefire-reports | 用例通过/失败与断言详情 |
| 服务端审计 | 主目录 runtime/service-requests.jsonl | 证明请求实际抵达 HTTP/Dubbo 服务 |

控制台前缀 `[TESTKIT CALL]`。同一个 callId 的 REQUEST 与 RESPONSE/ERROR 属于一次调用；runId/caseId/caseName 用于关联用例。
HTTP 400 在反向场景中可以是预期通过，不要仅按状态码判断用例失败。

日志先脱敏再截断；凭证、Cookie、token 等会被屏蔽。非 JSON 或无法安全序列化的正文可能显示 omitted，这不等于没收到响应。业务专有敏感字段通过 testkit.log.redactKeys 补充，敏感环境关闭正文。
原始报告不存正文，详细日志另外保存；要进入 Git 管理的证据，请复制经过检查的日志到 quality-assets/evidence，不要提交含密钥的输出。

### 9.2 常见问题

| 现象 | 先检查什么 | 怎么处理 |
| --- | --- | --- |
| Address already in use | 是否脚本和 IDEA 各启动了一份 | 停止多余实例，不乱杀所有 Java 进程 |
| HTTP ConnectException | health、18081、local.properties 是否仍为 8080 | 启动服务、改配置、删除旧 -D 覆盖、重新构建资源 |
| Dubbo Registry or direct URL required | 消费者配置是否加载 | local.properties 填 directUrl；检查 ProjectBootstrap ServiceLoader 文件 |
| Dubbo 连接拒绝/超时 | ::1:20891 是否监听，服务是否退出 | 先启服务，再执行 RPC；不要改成 HTTP URL |
| Dubbo 找不到方法/参数 | interface、method、parameterTypes、group/version | 使用真实契约，不改成示例类名或未经证实的 BO/VO |
| 只通过 1 条用例 | 是否只运行了 InitializationSmokeTest 或初始化 XML | 运行 GoldenOrder*Test，或 mvn test |
| 没有日志/没有正文 | 是否旧框架、bodies=false、控制台关闭 | 更新 Maven 框架、重新构建，检查 local 配置及 target/logs |
| SLF4J binder 警告 | 是否真正还有业务异常 | 新调用日志不依赖 binder，不能只凭此警告判失败 |
| IDEA 显示 exit code 0 但测试失败 | TestNG 的 Failures 数字 | 以测试结果为准，不以进程退出码代替测试判定 |
| 修改配置没效果 | target/classes 是否旧副本，-D 是否覆盖 | 改 src/main/resources，Reload Maven、Rebuild |
| 再生成提示文件已修改 | 是否改过生成测试代码/数据 | 这是保护，不删清单强行覆盖；新建模块或评审迁移 |

## 10. 通过故障注入证明断言有效

先保证基线正常。此操作会临时影响同一服务的两种协议，避免与其他人同时测试。

打开故障开关：

```powershell
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:18081/admin/fault -ContentType application/json -Body '{"enabled":true}'
```

然后分别运行 HTTP 和 Dubbo 的 mvn test，预期每个模块 3 通过、1 失败，失败是 GOLD-002 数量为零场景。
这次失败是验收目标，不要修改期望数据去迁就错误服务。

务必恢复：

```powershell
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:18081/admin/fault -ContentType application/json -Body '{"enabled":false}'
```

两个模块再次 mvn test，应各 4 条通过。最后健康检查 faultyZero=false。
不做故障验证时不要打开开关，服务恢复操作不要省略。

## 11. 一键从零复验，不覆盖原项目

本手册附带脚本可以复验整条工程链路。推荐新建隔离输出：

```powershell
cd E:\AITest\test\validation\local-http-dubbo-flow-20261018
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Verify-FullFlow.ps1 -Fresh -ConfigOnly
```

- Fresh：在 rechecks/manual-时间戳 下重新初始化两个项目，不覆盖原 http-tests/dubbo-tests。
- ConfigOnly：地址写入新项目 local.properties，不通过地址 -D 参数设置；日志输出路径可能临时覆盖到证据目录。
- 顺序：准备服务 → 初始化两模块 → PRD/TAD/用例/规格/代码生成 → HTTP/Dubbo 基线 → 故障检测 → 恢复复跑 → 保存原始证据和执行汇总。
- 脚本会在 finally 中恢复故障开关。
- 总报告位于主目录 quality-assets/evidence/run-时间戳/full-flow-report.json，里面的 projects 字段指出此次模块位置。
- 各模块 quality-assets/evidence/同轮次/ 下有 Maven 日志、JSONL、TestNG XML 和反馈。

不带 Fresh 时会复用原工程，检测到人工修改会停止；不要通过删除生成清单绕过保护。
该复验通过插件相同的生成服务完成，不是新版 IDEA 界面的逐按钮手工回归，二者不要混为一谈。

## 12. Git、反馈与目前的能力边界

建议版本管理：PRD/TAD、功能用例、接口规格、src/main/src/test、初始化与项目约定、生成清单、审核后的执行证据。
不要提交：target、runtime 进程状态、IDE 本机文件、密钥、未脱敏日志。插件不会自动替你 commit 或 push；完成后自行查看 git status、git diff 并评审提交。

当前黄金集没有使用远程 AI：它会返回固定的 TAD/用例/规格。因此样例工程跑通不代表任意需求都能正确分析。真实业务接入时要关闭黄金集、配置模型网关及 Key，并另做需求覆盖率验收。

默认模型反馈仍可能固定返回 blocked/not-run。验收程序从真实 JSONL 得出的 execution-feedback.yaml 明确标记为“验收程序派生”，不是模型自动闭环；原始模型反馈也保留，不能偷偷把它当成 passed。

目前通过的范围是本地 HTTP 和真实 Dubbo 直连、框架执行、日志和故障检测。数据库、注册中心、真实造数平台、页面、SDK 方法自动生成均未因此自动算通过。
