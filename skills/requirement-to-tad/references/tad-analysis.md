# TAD 分析规则

## 输入材料

尽可能收集以下材料：

- PRD、飞书正文、评审记录、原型说明、截图、流程图、接口字段。
- 同模块 `src/main` 下的已有文档。
- 同业务域的 TAD、TRD、STD 示例。
- 代码、API 文档、数据库字段、配置或开发说明中的明确技术线索。

## TAD、TRD 与 STD 的关系

将 TAD 视为总分析文档：

- TRD 聚焦业务规则、业务流程、角色、数据、状态和依赖。
- STD 聚焦有证据支持的技术实现、接口链路、时序、配置、缓存、任务和异常处理。
- 原始材料缺少技术证据时，允许 STD 内容较少，但不得凭经验补全实现。

## 推荐结构

```markdown
# 业务背景
## 1. 背景说明
## 2. 名词解析

---

# TRD 测试需求分析文档
## 1. 业务流程图
## 2. 业务规则
## 3. 业务依赖关系

# STD 系统测试分析文档
## 1. 技术实现
## 2. 时序图
## 3. 实现细节

## 附：规则合并说明
## 附：待确认问题
```

## 原子事实拆解

先把源内容拆成原子事实：

- 入口：页面、菜单、任务、接口、事件、定时任务。
- 角色：用户角色、权限、系统、上游域、下游域。
- 对象：订单、发票、员工、班次、园区、配送单、配置项。
- 动作：新建、编辑、查询、审批、取消、导入、导出、同步。
- 条件：状态、时间、阈值、枚举、灰度开关、权限、上游值。
- 分支：成功、失败、空值、重复、超时、降级、部分成功。
- 结果：页面展示、状态变化、记录生成、提示信息、下游事件。
- 依赖：服务、数据表、配置中心、外部系统、用户权限。
- 失败语义：阻断、重试、忽略、降级、补偿、保留原值。
- 数据规则：必填、唯一、格式、范围、边界、精度。

## 规则标准化

- 使用“条件 -> 动作 -> 结果”表达单条规则。
- 多条件组合优先拆成按场景命名的条件块；仅在必须横向比较多个相同字段时使用决策表。
- 使用状态迁移表达有生命周期的业务对象。
- 使用 Mermaid 流程图或时序图表达多分支流程。
- 合并重复规则，但保留最严格的约束。
- 为规则保留来源章节或编号，形成追溯链。

## 业务流程图展开规则

流程图的目标是让读者沿任一分支都能回答“下一步具体做什么、到哪里、看到什么”，而不是只展示抽象阶段。

### 规则先行与图文互补

1. 先从全部输入中提取完整业务规则清单，再开始画图。
2. 将改变触发、动作、路由、状态或最终结果的规则放入流程图。
3. 将字段映射、完整枚举、公式参数和大量静态文案保留在正文。数量限制、显隐、高亮、排序、滚动等内容形成独立操作分支或关键可观察结果时可以概括入图，否则保留在规则中。
4. 不允许流程图出现正文没有定义的判断条件，也不允许正文中的关键分支只写文字而没有流程节点。
5. 图负责说明业务如何流转，规则负责说明每一步依据什么、使用哪些数据、如何计算以及如何验证；两者互补，不逐字重复，也不各自遗漏关键信息。

### 端到端场景边界

- 默认让每张主流程图从真实页面入口、业务事件或定时触发开始，沿关键判断和动作走到自然业务结果。读者不查看其他流程图，也应能理解该入口下的完整主线。
- 公共匹配、加载、校验、初始化或结果组织步骤默认嵌入各端到端主场景，允许为保持完整性而适度重复。
- 只有同时满足以下条件才把公共能力独立成图：它本身构成可独立触发和验收的完整业务场景；具有清晰输入、独立判断和自然业务结果；被多个主场景复用；拆出后各主场景仍保留入口、触发、关键判断、路由和最终结果，不需要跨图拼接。
- 若拆分会让主场景从“取得匹配结果”“校验完成”“初始化完成”“处理完成”等中间产物开始，说明公共能力不应独立成图。
- 数量、显隐、高亮、排序、滚动等展示规则即使可观察，也不因内容较多而单独构造流程；只有其形成独立操作路径或改变后续业务分支时才入图。

### 拆图依据

- 拆图前先判断流程是否同构，不按页面、角色、模式或对象名称的字面差异直接拆图。
- 分支数量、判断条件语义、动作顺序、结果类型和后置效果一致，仅入口名称、业务对象、模式或目标名称可按上下文一一映射时，视为同构流程并优先合并。
- 合并后的流程图可选择两种表达：一是保留来源、角色、模式或对象判断并写出具体目标；二是在严格一一映射且下游完全对称时使用“当前来源”“对应模式”等上下文节点。采用第二种方式前，必须在名词解析或业务规则中列全映射，且不得隐藏任何结果差异。
- 只有某个上下文存在无法通过一一映射表达的额外条件、分支、动作、结果或后置效果时，才分别绘制流程图或在图中明确分区。
- 为清晰起见，允许在不同图中重复公共步骤，不为了去重制造跨图跳转或超大总图。
- 优先围绕核心业务对象的生命周期合并流程，例如创建/开通、变更和终止；数据字段或从属对象只有映射说明、没有独立触发条件时，不单独构造流程。
- 起点若带有明确适用条件，保留满足与不满足两条路径，不把前置条件直接改写成既成事实。

### 节点粒度

- 一个节点只表达一个动作、判断或可观察结果。
- 动作节点使用“动词 + 对象”，例如“加载匹配结果”“创建记录”“跳转目标页”。
- 判断节点必须是可回答的是/否或有限枚举问题，不使用“判断规则”“处理条件”等空泛名称。
- 路由节点写明具体目标页面、状态或业务对象，不写“进入对应页面”。
- 后置效果单独成节点，例如提示文案、结果置顶、列表定位、回流来源页、刷新数据或状态变更。
- 起点节点直接写真实入口或触发事件，不使用仅表达图形形式的“开始”。

### 分支要求

- 判断节点的每条边写出明确条件或选择值。
- 每条边的下一节点写明立即执行的具体动作。
- 不把多个不同结果汇总为“处理结果”；若结果不同则继续拆分。
- 不让流程结束在中间动作上，终点前必须出现用户或系统可观察的结果。
- 不要求所有分支连接同一个“结束”节点。原文明确没有后续动作时，可直接以“结束”“无需操作”“不发送”等自然结果终止；其他分支停在各自明确的页面、状态、提示或业务结果。

### 绘制步骤

1. 按真实入口或触发事件列出端到端主场景。
2. 列出主场景中的公共步骤，默认保留在主图；仅当公共能力本身是完整可验收场景，且拆分后主图仍端到端完整时才单独成图。
3. 找出产生路线差异的判断点，并判断对称入口是否可以在一张图内明确展开。
4. 为每个分支写出立即动作、具体目标和关键后置结果。
5. 将字段、枚举、公式和大量静态内容移入业务规则；保留会形成独立操作路径或关键可观察结果的交互节点。
6. 将分支与业务规则逐项对照，确认没有缺边、跨模式或错误回流。
7. 从每个入口沿每条路径人工走读到自然终点，确认不依赖其他图也能理解完整业务主线。

## 高密度配置与枚举保真

不得为了简洁丢失源文档中可直接测试的数据。处理大表、精确内容、静态映射和条件矩阵时执行以下步骤：

1. 记录源表名称、表头、有效数据行数和关键维度。
2. 将每一行拆为条件、动作和结果；完全重复的行才允许合并。
3. 合并时给出覆盖的原始组合，确保各条件维度、时间节点、参与对象和结果差异仍可还原。
4. 数量较大的静态映射按业务对象分组列出；只有在横向比对确实更清楚时才使用附表。
5. 输出后复核枚举与组合数量，任何可测试记录都不得无说明减少。

若映射值属于地址、精确正文、提示语或枚举，应原样保留；不得改写地址、数字、比较符、标点或变量名。

### 表格内容与上下文关联

1. 提取表格时记录表名、表头、总行数、有效数据行数，并逐格保留原文；合并单元格、换行、空值、占位符和重复值也不得跳过。
2. 按源表实际表头将同一行各列视为一条完整记录。先保全记录，再判断其能否直接验证、需要跨章节解释或只能列为待确认；不预设表格必须包含某组固定列。
3. 说明和备注是规则证据，不是可选内容。其中的条件、分类、默认值、映射、例外、公式、环境差异和章节引用必须进入业务规则分析。
4. 单元格出现“根据某规则”“同上”“见某章节”等引用时，回读目标内容，将当前记录与目标规则建立上下文关系，并把合并后的条件、动作和结果展开为可测试场景；最终正文不能只保留“按某规则处理”或“关联某章节”的引用说明。引用目标缺失或编号错位时保留记录并标记TODO。
5. 记录暂时不可用、部分列为空或为占位符、缺少标识或无法从现有材料验证时，不删除该行；原样记录已知信息并说明不可验证范围。
6. 输出后执行反向核对：源表每条有效记录都能在TAD正文中定位；若多行合并表达，明确列出覆盖的原始记录，避免因归纳丢失说明或备注语义。

### 图片型表格转录

1. DOCX、PDF、网页或截图中的字段表和决策矩阵必须作为结构化需求读取，不能只记录“存在一张图片”。
2. 先识别表头和列数，再逐行转录；对跨行文本、换行枚举、彩色备注、链接文字、环境标识和长数字ID进行原样保留。
3. 同名字段出现多行时按独立记录处理，除非各列内容完全一致；不能只保留其中一行。
4. 图片中的说明列和备注列与字段列具有相同证据等级。分类条件、优先级、默认值、例外和冲突必须进入业务规则。
5. 同一条件同时指向多个结果、规则存在覆盖或优先级不明时，不自行选择路径；在规则旁标记冲突及其测试影响。
6. 完成转录后按图片的有效行数、枚举数量和关键标识逐项反查；过程清单用于内部校验，默认不作为TAD正式章节输出。

## 多维交互与输出规则

对通知、审批、分流、展示、导入导出或其他多维交互，按实际存在的维度提取：

| 字段 | 要求 |
|---|---|
| 适用对象 | 角色、状态、范围或其他适用条件 |
| 触发 | 事件或时间条件、状态条件、边界日期 |
| 参与对象 | 保留源需求中的明确角色名称，不用上位概念替代 |
| 渠道/载体 | 页面、消息、文件或外部系统；未说明则写待确认 |
| 内容 | 对应模板、字段、文案或输出结构 |
| 变量 | 变量名、取值来源、计算公式和空值语义 |
| 动作 | 操作文字、目标匹配规则和执行结果 |
| 展示 | 标题、正文、颜色、图标、显隐等可观察结果 |

维度较多时，按源需求的自然业务顺序分层展开；只有文字会造成重复或难以比对时才使用决策表。必须保留改变业务含义的精确文案、提示、变量和结果差异。

## 表格使用门槛

- 默认不使用表格表达业务规则。
- 名词、条件、动作、结果、依赖、精确内容和待确认项优先使用标题、编号与列表。
- 只有同时满足“字段固定”“记录重复”“读者需要横向比较”三个条件时才使用表格。
- 即使源 PRD 使用表格，也应先判断是否可转成更易读的场景块；转换后必须保持每一原始行可追溯。
- 完成前统计 Markdown 表格数量，逐张说明其不可替代性；无充分理由则改成列表。

## 业务规则最低颗粒度

每个业务场景至少写清原需求能够确定的适用对象或入口、触发或选择、业务动作和可观察结果。原需求明确存在时，再补充前置条件、反向分支、字段、公式、参与对象、精确内容、边界、空值、重复、状态冲突和依赖缺失；不得为了补齐固定维度而虚构事实或生成探索性 TODO。

流程图中的每个判断节点必须在业务规则正文中有对应说明，正文中的每个关键分支也必须能在流程图中找到。不得用含义模糊的“是否符合条件”替代原文能够明确指出的配置、状态或时间条件。

## 业务规则输出格式

### 通用层级与排版

- 按业务机制和决策关系归并三级标题，标题优先使用“业务对象或能力 + 规则”，不按页面控件、字段类型或原子事实类别机械拆章。
- 三级标题表示可独立理解和测试的完整业务能力；同一链路的触发、处理、结果组织、展示契约和反向分支优先集中表达。
- 四级标题只按不同入口、角色、人群、模式或状态形成的独立子流程分组，不为每个选择项、字段或按钮分别建立四级标题。
- 主题内部默认使用有序列表，规则项写成 `1. **<规则名称>**：`；关联字段和分支使用缩进项目列表。
- 对原文中的精确枚举、阈值、结果类型、页面或状态名称、提示文案和禁止项适度加粗；不对整段文字或模型自行概括的术语加粗。
- TODO 紧跟产生疑点的规则块；同一根因只保留一项。

### 按需求形态选择结构

- **查询、匹配、筛选和结果展示类**：在同一主题内优先按“触发机制 → 结果分类或计算规则 → 展示限制 → 导航或交互 → 卡片、列表或结果内容 → 原文明确的空结果”组织。不得把匹配、分类、数量限制、导航和卡片字段仅因名称不同拆成多个三级标题。
- **跳转、回流和业务分流类**：三级标题表示完整的交互或路由能力；四级标题按入口、角色、模式或状态分组；组内按选择项、触发事件或状态变化编号，逐项展开动作、路由与后置表现。
- **新建、编辑和校验类**：优先按“入口与权限 → 输入或回填 → 校验与限制 → 提交动作 → 成功结果 → 原文明确的反向分支”组织。
- **生命周期、审批和状态迁移类**：优先按“触发状态 → 前置条件 → 执行动作 → 新状态与输出 → 禁止或不处理分支”组织；状态差异较多时按状态增加四级标题。
- **字段映射、同步和通知类**：优先按“触发与适用范围 → 来源数据 → 映射或内容规则 → 目标或参与对象 → 输出结果 → 原文明确的失败处理”组织；字段清单保持完整，但不为单个字段建立碎片标题。

### 场景语义标签

场景内部只选择原需求实际存在的标签，不强制补齐全部维度：

- **条件**：适用前提、状态或时间条件。
- **动作**：系统立即执行的业务操作。
- **路由判断**：不同入口、角色、模式或状态对应的具体目标。
- **结果**：业务对象、页面或状态发生的变化。
- **表现**：定位、置顶、刷新、显隐、排序或回流等可观察效果。
- **提示**：原需求明确给出的提示文案。
- **注意**：原需求明确要求的不执行、隐藏、禁止或例外情况。

没有对应事实时不输出该标签；同一条短规则能够直接表达条件、动作和结果时，不为套格式强行拆成多个标签。

### 通用输出骨架

```markdown
## 2. 业务规则

### 2.1 <查询、匹配或展示能力>规则

1. **触发机制**：
   - <触发条件及处理结果>
2. **结果分类或计算规则**：
   - **<类别A>**：<匹配、筛选或计算规则>
   - **<类别B>**：<匹配、筛选或计算规则>
3. **展示限制**：
   - <数量、边界、高亮或显隐规则>
4. **导航与交互**：
   - <操作及可观察结果>
5. **内容规范**：
   - **<对象A>**：
     - <字段或展示要求>

### 2.2 <跳转、回流或分流能力>规则

#### 2.2.1 从“<入口、角色或模式>”进入

1. **选择“<结果或操作>”**：
   - 动作：<立即执行的业务动作>
   - 路由判断：
     - 若<条件A>：<具体目标>
     - 若<条件B>：<具体目标>
   - 表现：<定位、置顶、刷新、回流或显隐>
   - 提示：<原需求明确的提示文案>
```

骨架只约束结构，不要求需求必须同时包含两个主题或全部规则项。删除没有事实支撑的占位项，并根据需求形态替换主题和规则名称。

### 组织与准确性约束

- 以最少且完整的稳定主题为优先。只有拆分后的每个主题都具有独立业务目标、无需跨章节拼接才能回答完整规则，且信息密度足以支撑独立测试时，才拆成并列主题。
- 同一主题先写公共机制，再写限制、展示和反向分支；公共规则只写一次，差异规则按入口、角色、模式或状态展开。
- 基础动作和路由一致时可以合并相近选择项；若其中一个子类型具有额外的提示、置顶、高亮、回流或状态变化，必须在合并规则内单独限定该子类型，或拆成相邻规则，不得把额外效果扩大到全部选择项。
- 输出风格不得成为事实来源。原文没有出现的技术名词、业务对象、提示、页面、状态或处理结果不得因骨架示例而补入；不得把“置顶”改写为“置顶或高亮”，也不得改变滚动目标、比较符、阈值或提示文案。
- 不为凑结构重复同一事实，不省略原文明确的字段、阈值、显隐条件和结果差异，不把生成方法、回链过程或完整性核对写入正文。

### 流程与规则双向校验

- 流程图中的每个判断分支必须能在业务规则中找到对应条件、动作和结果。
- 业务规则中改变主路径的路由、回流、状态变化及关键提示、置顶、定位结果必须能在流程图中找到节点。
- 若某项只有规则没有流程节点，判断它是静态约束，还是形成独立操作分支或关键可观察结果。静态字段、枚举、公式和文案不强制补节点；会改变操作路径或读者理解的关键交互结果应补入流程。
- 若某个流程节点无法写成可测试规则，说明节点仍过于抽象，应继续拆解。
- 为每个流程节点确认正文规则归属，为每条流程规则确认图中节点；该映射仅用于内部校验，无需强制输出成表格。

## 可见文档表达

- 原文存在章节号、需求号或规则号时保留；原文没有编号时，沿用目标目录黄金样本的编号和来源标签风格。黄金样本使用 `BR-*` 或逐条“来源：”时可以采用，使用自然编号时不额外添加。
- 来源位置和表格行映射可作为内部完整性检查，不默认写入正式 TAD。
- TODO 就近放在相关主题后；同一根因造成的多个疑点合并描述，写清对流程、规则或测试设计的影响。写完后执行必要性判断：若不确认该问题，仍能依据现有材料确定当前流程和可观察结果，则删除该 TODO。
- 不输出抽取步骤、行数核对、备注回链、生成策略或黄金样本比较等过程说明。

## 截图与原型证据

- DOCX、PDF 或网页需求包含截图时，渲染并检查相关页面，不只做文本提取。
- 只记录肉眼可观察的 UI 事实，例如卡片颜色、标题、按钮文字、字段顺序和跳转入口。
- 在规则中标注“来源：PRD 截图/原型”，区分正文规则与视觉证据。
- 不从截图猜测模板 code、接口、组件名、选择器或实现框架。

## 待确认项判定

仅在不确定性会改变当前需求的适用条件、流程路径、业务动作或可观察结果时生成 TODO，主要包括：

- 标题、正文、表格、备注、截图或流程图之间存在无法同时成立的规则冲突。
- 入口、角色、模式、状态、对象或术语在上下文中无法建立明确映射，导致路由或规则归属不确定。
- 决定分支或结果的关键条件、枚举、阈值、字段值为空或未定义。
- 正文引用配置表、附件、设计稿或其他章节，但引用目标缺失，且缺失内容会影响当前业务预期。
- 示例与规则口径不一致，无法判断应采用哪一个结果。

以下情况默认不生成 TODO：

- 需求没有主动描述的常规边界、分页、排序并列规则、精度、状态保留等可扩展测试问题。
- 缓存、并发、超时、重试、限流、降级、补偿、幂等等实现或非功能策略没有技术证据。
- 基于经验可以继续追问、但不影响当前明确主流程和验收结果的问题。
- 与本期正文没有引用关系的空表、空章节、占位符或空单元格。

对空表、空章节和缺失单元格先判断其是否被正文引用，以及缺失内容是否改变当前条件、动作、路由或结果；不满足时不生成 TODO。TODO 必须写清冲突或缺口所在、需要确认的具体口径及其对测试设计的影响。同一根因只保留一项，不把一个缺口拆成多个探索性问题。

## 业务依赖与输出

- 将依赖输入与业务输出分开描述。
- 输入说明数据/配置来源、提供内容和影响范围。
- 输出说明生成或更新的业务对象及外部可观察结果，不把业务输出虚构成具体技术接口。
- 失败、重试、幂等、补偿等语义只有原文明确时才写结论。原文未说明且不影响当前明确业务路径时，仅保持证据边界，不生成探索性 TODO；只有依赖失败会使当前业务预期无法确定时才列为待确认。

## 业务规则分类

按功能实际情况选择分类：

- 查询、筛选、列表和详情展示。
- 新建、编辑、删除、启用、停用。
- 必填、格式、唯一性、枚举、边界和精度。
- 条件展示、隐藏、禁用和自动回填。
- 导入、上传、导出和下载。
- 审批、状态迁移、取消和失效。
- 上游回调、下游同步、定时任务和消息事件。
- 权限、数据范围、灰度和功能开关。
- 异常、降级、重试、幂等和并发。

## STD 证据边界

只有下列证据存在时才写技术分析：

- 明确命名的接口、DTO、事件、数据表、配置、缓存、定时任务或中间件。
- 需求中明确写出的实现说明。
- 用户提供或仓库内存在的代码与技术文档。

证据不足时写 `未发现明确信息`，或增加待确认项。不得虚构内部服务、字段、选择器、路由、SQL 或提示文案。

没有代码或接口证据时，技术实现章节先概括需求材料实际提供的技术线索，再按接口、任务、数据、缓存、路由、重试等相关类别列出“未发现明确信息”；不得只复制空泛模板，也不得把待确认技术类别写成已经存在的实现。

用户提供的期望 TAD、黄金样例或历史分析文档默认只属于格式参考，不属于当前需求的技术证据。仅在以下任一条件成立时，才能生成 STD 调用链：

- 当前工作区可访问对应代码，并能定位类、方法和调用关系。
- 当前需求材料提供明确的接口或实现说明。
- 用户明确确认某份技术文档就是当前需求的有效实现证据。

若以上条件均不成立，STD 使用以下最小表达，不生成接口清单、Job、cron、数据库、缓存或时序图：

```markdown
# STD 系统测试分析文档
## 1. 技术实现
未获取到可验证的代码、接口文档或技术实现材料，无法分析具体技术实现。

## 2. 时序图
无法获取实际调用链，不生成时序图。

## 3. 实现细节
接口、任务调度、数据表、缓存、重试、超时、降级和幂等设计均待补充技术证据后分析。
```

## 输出位置

- 默认在原始需求文件所在目录生成 Markdown。
- 文件名从需求标题与正文核心范围共同提炼，采用“业务对象 + 核心能力”。
- 去除方括号前缀、训练/需求序号、版本号和“需求”“PRD”“方案”“文档”等非业务词。
- 当标题宽泛时，以正文明确交付范围提炼文件名。
- 不因样例文档所在目录改变输出目录。
- 同名文件存在且没有明确覆盖授权时，生成候选文件或先说明冲突。

## 质量检查

- 每条业务规则至少能生成一个测试用例。
- 每个流程分支都有明确预期结果。
- 原文明确列出的枚举、节点和状态全部保留。
- 阈值、限制、精度、日期范围、提示语、路由条件和角色条件未被改写。
- 依赖关系包含失败语义。
- 图和文字之间不存在矛盾。
- 冲突或可疑示例进入待确认项，不静默修正。
- 每张主流程图都能从真实入口独立走到具体业务结果，不依赖另一张图补全，也不从公共处理结果处开始。
- 业务规则使用最少且完整的主题表达；同一链路的触发、处理、结果组织和展示约束没有被机械拆散，路由与分流差异按入口、角色、模式或状态集中说明。
- 每个 TODO 都会影响当前流程或可观察结果；不存在常规边界、实现参数、非功能策略或异常兜底类探索性问题。
