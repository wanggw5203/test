# 需求转 TAD 分析

把原始需求提炼成可验证、可追溯、可继续生成测试用例的 TAD 文档。开始前必须完整阅读 [TAD 分析规则](references/tad-analysis.md)。

## 收集上下文

优先收集与目标功能最接近的材料：

- 原始 PRD、飞书内容、Axure 导出、截图、流程图、评审记录和接口说明。
- 同模块 `src/main` 下已有需求或分析文档。
- 同业务域的 TAD、TRD、STD 示例及术语。
- 代码、接口、表结构或配置中的明确技术证据。

按以下优先级确定输出基准：

1. 用户明确提出的结构与表达要求。
2. 目标需求目录下已有的稳定 TAD 模板。
3. 同业务域已有 TAD 的通用表达习惯。
4. 本 skill 的默认结构。

同一目录存在多份均被认可、但结构不同的黄金样本时，不把它们强行合并成单一固定模板。按业务机制、流程复杂度、规则密度和材料类型选择最接近的样本风格：交互与查询类、生命周期与通知类、字段映射与同步类可以采用不同的流程边界和规则层级，但必须遵守共同的完整性与证据约束。

用户提供的期望文档只用于提炼结构、章节层级和表达风格，除非用户明确说明它也是事实来源。不得从样例复制业务结论、接口、Job、cron、表、缓存或调用链。

信息冲突时，保留原文并记录冲突，不得自行修正业务含义。

## 执行分析

1. 识别角色、入口、对象、动作、条件、分支、结果、依赖、异常、数据和状态。
2. 把复合描述拆成原子事实，逐条保留来源位置。
3. 使用“条件 -> 动作 -> 结果”改写为可验证业务规则。
4. 先完成业务规则提取，再决定流程图边界。默认按真实入口、触发事件和最终结果表达端到端主场景，读者沿一张图即可从入口走到具体业务结果。公共匹配、校验、加载或展示步骤默认保留在主场景中并允许适度重复；只有该能力本身构成可独立执行和验收的完整场景、被多个主场景复用、单独成图显著降低复杂度，且拆分后各主场景仍不依赖跨图补全主线时，才允许独立成图。不得让主场景从“取得结果”“校验完成”“处理完成”等公共流程输出处开始。
5. 优先用分层编号、条件块和项目列表表达规则；对生命周期对象使用状态迁移，对多分支流程使用 Mermaid。只有当行列对照明显比文字更清晰时才使用表格。
6. 将有技术证据的内容写入 STD；没有证据的内容写为 `未发现明确信息` 或列入待确认项。
7. 合并重复规则，但保留最强约束、精确枚举、阈值、提示语和角色条件。
8. 仅当当前可访问材料中确实包含对应代码或技术文档时，才检索 Job、Dubbo/API、通知记录、配置、缓存和数据库实现并补足 STD。不能访问代码、检索不到实现，或只能在样例 TAD 中看到技术结论时，不得生成链路；STD 明确写明“未获取到可验证的代码或技术证据，无法分析”。
9. 仅为会改变当前需求流程、适用条件、业务动作或可观察结果的真实不确定性生成 TODO，包括材料之间明确冲突、术语或上下文无法对齐、关键条件缺失、被引用材料缺失且无法据此确定预期。不要把需求未主动描述的常规边界、实现参数、非功能策略、异常兜底或可进一步探索的问题扩展成 TODO。每个 TODO 写完后反问“未确认时是否无法确定当前规则的路径或预期结果”；答案为否则删除。同一根因只保留一项。
10. 对多条件、多角色、多状态或多结果规则逐组完整展开。优先使用“场景标题 + 条件 + 动作 + 结果”结构，不用“普通场景”“其他情况”等概括替代原文明确组合。
11. 对源文档中的枚举、映射、精确文案、操作项、提示语和校验条件建立完整性清单；正文可归纳逻辑，但必须保留全部可测试数据。
12. 对源文档表格先逐表、逐行、逐单元格提取，再分析内容是否可用。按源表实际列定义完整保留标题、数据、说明、备注、空值和跨章节引用；不得因某列为空、暂时无法验证或含义不完整而提前丢弃记录。说明或备注引用其他章节时必须回读对应上下文并形成关联规则。
13. 当字段表、配置表或决策矩阵以图片呈现时，必须逐图查看并转录表头、全部有效行及每个单元格；精确ID、枚举、公式、链接文字、默认值、说明和备注均需保真。图片模糊处不得猜测，需标记待确认。转录后按图片行数和关键值反向核对。
14. 阅读截图和原型中的可观察信息，记录页面颜色、标题、按钮、显隐、布局和跳转等测试预期，并标明其来源为截图或原型；不得从视觉样例推断技术标识。
15. 扫描空表、空章节、只有标题的规则和未填写单元格；仅当其被正文引用，或缺失内容会改变当前规则的条件、动作、路由或结果时，才就近标记 TODO。与本期范围无关联的空占位不得扩展成探索性问题。
16. 业务规则按可独立理解和测试的业务机制自然归并，不预设主题名称、数量或固定顺序，并以最少且完整的稳定主题为优先。同一链路中紧密关联的触发、处理、结果组织、展示约束和反向分支优先放在同一主题，先写公共机制，再写差异；路由、状态迁移或分流规则优先按入口、角色、模式或状态集中展开。只有拆分后的每个主题都具备独立业务目标、无需跨章节拼接才能理解，且信息密度足以支撑独立测试时，才拆成并列主题。不得按控件、字段类型或原子事实类别机械拆章；根据需求形态套用参考文件中的业务规则输出格式，使用有序编号、加粗规则名称和按需语义标签，只有不同入口、人群、模式或状态形成独立子流程时才增加四级标题。
17. 绘图前对不同入口、角色、模式或对象执行流程同构判断，结构对称时优先合并。目标映射存在两种合法表达：当各上下文结果存在需要单独断言的差异时，在图中保留来源判断并写出具体目标；当映射严格一一对应、下游动作和结果完全对称，且名词解析或业务规则已明确列出映射时，可以使用“当前来源”“对应模式”等上下文节点。不得在映射未定义或结果存在差异时用抽象节点隐藏路由。
18. 流程图优先承载入口、触发、判断、动作、路由、状态变化和关键后置结果。字段清单、完整枚举、公式参数和大量静态文案放在业务规则中；数量限制、显隐、高亮、排序、滚动等展示约束默认留在业务规则，只有它们会改变后续操作路径、形成独立判断分支或决定最终业务结果时才进入流程图，避免展示细节挤占端到端主线。
19. 每个判断分支的下一节点必须写明具体动作或目标，跳转后的提示、回流、定位、置顶、刷新等关键结果使用独立后置节点表达。起点使用真实入口或触发事件，终点使用自然业务结果；不为形式统一增加“开始”或让全部分支汇入同一个“结束”节点。原文明确无后续动作时允许直接以“结束”“无需操作”或“不发送”等自然结果收口。
20. 最终文档只呈现业务事实、规则、证据边界和必要TODO。规则编号与来源标签优先沿用目标目录黄金样本的稳定风格：若本地模板使用 `BR-*` 和逐条来源标签则保持一致；若使用自然编号则不额外添加。无本地基准且用户未要求审计追溯时，默认使用自然编号，不输出“备注回链依据”“完整性核对”等生成过程信息。

## 生成文档

默认使用以下一级结构；目标仓库已有稳定模板时，必须沿用本地模板：

```markdown
# 业务背景
# TRD 测试需求分析文档
# STD 系统测试分析文档
```

至少包含业务流程、业务规则、依赖关系和技术实现证据。规则合并说明、来源编号与待确认问题的呈现方式服从本地黄金文档，不强制增加本地模板不存在的附录。让每条业务规则都能直接转成一个或多个测试断言。

按独立业务场景拆分 Mermaid 图，业务规则按主题分节。STD 的详细程度由证据决定：有代码证据才列端点和时序；没有证据时保留 STD 标题并说明无法获取链路，不用占位图模拟实现。

## 校验结果

完成前检查：

- 每条规则都有明确条件和可观察结果。
- 每个流程分支、枚举项、状态和边界均被保留。
- 每张配置表的原始行数、枚举数量和输出 TAD 的记录数量一致，或有明确的合并映射说明。
- 每张源表均已核对表头、有效数据行数及每个单元格；处理逻辑/备注中的规则、引用和限定词均已进入正文或待确认项。先完成保全核对，再判断字段可用性，不以不可用为由删除原始字段。
- 每张图片型表格均已逐行转录并按原图复核；精确标识、公式、枚举、默认值和备注没有因OCR、缩放或换行而改写。
- 每个多维业务场景都覆盖适用对象、条件、动作、结果、涉及数据和可观察结果。
- 已检查空表、空章节和缺失单元格；只有会影响当前条件、动作、路由或结果的缺失才转成待确认项。
- 已执行表格必要性检查：能用清晰列表表达的内容不使用 Markdown 表格；静态映射很多时也优先按对象分组列出。
- 已执行层级检查：三级标题代表稳定业务主题，四级标题仅用于主题内的独立子流程；不存在只有一两行内容的碎片化标题。
- 依赖项仅在原需求明确提出，或其失败会使当前业务预期无法确定时分析失败、超时、重试、降级或补偿语义；不为常规技术完备性追加探索性 TODO。
- Mermaid 与文字规则一致。
- 流程与规则互补：每个流程判断、动作和结果都能定位到正文规则；正文中会改变主路径、路由、状态或关键结果的规则都有对应流程节点；字段、枚举、公式和静态展示细节保留在相关业务主题中，不强制逐项画成节点。
- 每个判断节点的所有分支都有明确边标签和具体下一步，不存在“处理结果”“进入对应页面”“按规则执行”等可被继续拆解的概括节点。
- 每条流程终点都包含可观察业务结果；跳转后的提示、回流、定位、排序、刷新或状态变化未被省略。
- 流程边界选择有明确依据：每张主场景图从真实入口走到具体业务结果，不依赖阅读另一张图补全；独立公共流程本身构成完整可验收场景，且拆分后没有让主场景从公共输出处开始。
- 已对不同入口、角色、模式和对象完成流程同构检查：结构对称的流程已合并；采用抽象上下文节点时，一一映射已在名词或业务规则中明确，且没有隐藏结果差异。
- 流程图没有为统一形式增加“开始”节点或公共“结束”节点；字段和大段静态内容未挤占业务主线，关键交互分支及其可观察结果也未被遗漏。
- 没有为仅提供字段映射、但未提供触发条件的从属对象虚构独立业务流程。
- 最终文档不包含仅用于生成自检的过程性章节或分析方法说明；规则编号和来源标签与目标目录黄金样本风格一致。
- 没有虚构接口、字段、路由、数据库、选择器或提示语。
- 每个待确认项都来自材料冲突、上下文不一致、关键条件缺失或影响预期的引用缺口，包含疑点及其对测试设计的影响；不存在仅为补齐边界、实现参数、非功能策略或异常兜底而提出的探索性问题。
- 业务规则已按最少且完整的业务机制归并；同一链路的触发、处理、结果组织和展示约束无需跨多个碎片章节拼接，路由与分流差异按入口、角色、模式或状态集中表达。
- 业务规则已选择与需求形态匹配的输出结构；三级标题、四级入口分组、有序规则项和按需语义标签符合参考格式，没有强行补齐原文不存在的标签或事实。
- 文档的标题层级、用词和规则颗粒度与用户要求一致。
- 所有写入 STD 的接口、Job、cron、表名和缓存均能在代码或技术材料中定位；不能定位的内容不得沿用样例猜测。

## 输出约束

- 保留源文档中的中文业务术语。
- 默认写入原始需求文件所在目录；只有用户明确指定其他输出目录时才改变位置。
- 生成文件名前，结合需求标题、背景和核心范围提炼“业务对象 + 核心能力”。删除编号、版本标记以及“需求”“PRD”“方案”“文档”等过程性词；不要机械复制源文件名，也不追加 `-TAD`。
- 不静默覆盖已有文件；覆盖意图不明确时创建新文件或说明冲突。
- 原文已有需求编号、章节号或规则号时保留其追溯关系；原文没有编号时，按目标目录黄金样本选择 `BR-*` 编号、来源标签或自然编号，且同一文档保持一致。无本地基准时默认使用业务主题和规则标题供后续用例引用。
