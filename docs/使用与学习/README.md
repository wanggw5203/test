# 三个工程：使用说明与框架学习入口

本文档以 2026-10-18 当前源码为准。三个工程不是三套互不相干的演示项目，而是生产测试资产的一条工具链。

| 工程 | 所在目录 | 交付物 | 谁使用 |
| --- | --- | --- | --- |
| 自动化框架 | `E:\AITest\test\baseTest` | Maven 公共依赖包 | 自动化项目通过依赖使用，框架维护者改源码 |
| 工程初始化器 | `E:\AITest\test\tools\automation-project-initializer` | CLI JAR、HTTP/Dubbo/SDK 工程模板 | 项目创建者；插件也可以调用 |
| IDEA 插件 | `E:\AITest\test\tools\ai-test-flow-idea-plugin` | IDEA ZIP 插件 | 测试人员在项目中处理需求、生成测试资产 |

另有 `tools/api-test-scaffold-generator`，它是插件内置的确定性脚手架生成组件，不是要求用户单独启动的第四个服务。

## 必须先理解的五句话

1. 框架不是订单服务，不需要像后端服务一样常驻启动；业务测试 JVM 加载框架依赖执行。
2. 初始化器创建测试工程，不启动被测系统，也不负责分析 PRD。
3. 插件读取、处理并写回 Git 项目中的资产；生成成功不等于接口测试已经通过。
4. 自动化项目是工具链的产物，有自己的 POM、main/test、配置和 Git 历史，不要把业务测试不断加到框架源码里。
5. 本地 `service` 是被测系统，必须先启动，HTTP 和 Dubbo 用例才能真正调用；初始化冒烟通过不能替代业务接口通过。

不要在旧 `requirement-order-flow-20261018` 和当前 `local-http-dubbo-flow-20261018` 之间交叉找文件。本文本地演练统一以后者为准；正式业务可以使用自己的 Git 工程。
