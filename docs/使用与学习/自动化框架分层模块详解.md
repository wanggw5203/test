# 自动化框架分层模块详解

> 历史分册：内容已合并到 [Testkit自动化框架完整学习手册](../../baseTest/Testkit自动化框架完整学习手册.md)。后续只需阅读合并版，本文件保留用于历史链接。

这不是技术名词清单。阅读目标是：能沿着一条用例解释数据从哪里来、使用谁的身份、在哪准备资源、怎样调用、为什么失败、如何释放，并知道改动应放在哪一层。

所有源码路径相对于 `E:\AITest\test\baseTest`。核心包为 `io.testkit.basetest`，适配层包为 `io.testkit.adapters`。文中的业务接入示例需要自行落地，不表示当前订单演练已经接入账号/造数平台。

## 1. 先认识分层

```text
业务资产层        PRD / TAD / 功能用例 / 接口规格 / YAML / JSON5
测试编排层        TestNG测试类 / BaseTest / API封装 / 业务DataBuilder
运行时与生命周期  ProjectBootstrap / AutomationRuntime / Listener / Context
公共能力层        数据驱动 / 身份 / Mock / 断言 / 日志 / 报告 / 租约
协议与适配层      HTTP / Dubbo / SDK / JDBC / Kafka / Job
外部环境          被测服务 / 账号平台 / 造数平台 / 数据库 / 注册中心
```

这是一种职责划分，不表示每行都对应一个 Maven 模块。数据驱动、身份、HTTP 等多数在 base-test-toolkit；Dubbo/Kafka/XXL-JOB 等在 enterprise-adapters；公司业务实现放自动化项目或独立企业适配包。

为什么分层：需求变化不应该修改网络客户端；Token 平台变化不应该重写每个测试；增加日志不应该让每个用例复制 println；换 Dubbo 协议不应该重写 YAML 解析器。

## 2. 模块总览与阅读入口

| 模块 | 核心入口 | 主要解决的问题 |
| --- | --- | --- |
| 基础生命周期 | BaseTest、runtime/PortableTestNgListener | 上下文绑定、每次调用的资源与结果收尾 |
| 数据驱动 | data/DataDriveUtil、CaseContext、TestCaseData | 数据和测试逻辑分离，参数绑定可校验 |
| 配置 | config/ConfigLoader、TestEnvironment、项目 ProjectSettings | 环境可切换、类型与来源可追踪 |
| 身份 | identity/IdentityProvider、IdentityContext、UseIdentity | 角色选择、账号租用、线程隔离、释放 |
| 造数 | data/DataFactory、DataPreparationRequest、业务 DataBuilder | 运行前依赖数据准备，不把固定文件当真实造数 |
| 返回值与清理 | ReturnValueContext、runtime/CleanupStack | 单次调用数据传递与失败后清理 |
| Mock | mock/MockEngine、MockSession、MockScenario | 可控依赖场景和生命周期 |
| HTTP | http/ApiClient、ApiResponse | 通信、认证入口、目标约束、诊断 |
| Dubbo | enterprise-adapters 中 dubbo/DubboClient | RPC 泛化调用、类型签名、引用生命周期 |
| SDK | sdk/SdkInvoker | SDK 调用包装与结果采集扩展 |
| 断言 | assertion/JsonDiff、JsonContract、Await | 结构化差异、契约、有限等待 |
| 执行装配 | runtime/AutomationRuntime、RuntimeRegistry、RuntimeProvider | 显式注入公共能力和调用级隔离 |
| 日志报告 | ProtocolCallLog、JsonLinesResultPublisher、TraceContext | 调用诊断、执行结论、关联追踪 |
| 企业组织 | enterprise 包、lease 包 | 归属、计划、分片、目标策略、共享资源租约 |
| 外部能力 | database、discovery、job，适配层 kafka/xxljob | 数据验证、发现、异步任务和消息接入 |

## 3. 一条业务用例的真实执行链

以生成的 GoldenOrderHttpTest 为例：

1. Maven Surefire 或 IDEA 启动 TestNG。
2. 项目 ServiceLoader 注册的 ProjectBootstrap 在 execution start 加载环境默认配置，并安装 AutomationRuntime。
3. 测试类的 BeforeClass 创建业务 API 封装。此时配置应已就绪。
4. DataProvider 调用 DataDriveUtil，根据测试类包名和 suite 名找 YAML。
5. YAML 每条有效 case 被转换为 CaseContext、request、expected，一条 case 对应一次测试调用。
6. BaseTest 的 BeforeMethod 从参数中找到 CaseContext，绑定当前用例。
7. PortableTestNgListener 在测试方法执行前建立运行时/Trace 范围；若声明身份则获取身份；若有 mockId 则打开 MockSession。
8. 测试方法调用业务 DataBuilder.prepare，并登记 deferCleanup。
9. API 封装调用 ApiClient 或 DubboClient，记录请求和响应/异常。
10. 测试方法断言 HTTP 状态及业务响应，或断言 RPC 业务体。
11. Listener 收尾 Mock、身份和运行范围；BaseTest 的 AfterMethod 执行已登记清理并移除用例与返回值上下文。它们是各自负责的收尾边界，不应依赖猜测的全局顺序。
12. Listener 发布成功、失败、跳过或配置失败等结果，执行结束后形成汇总；项目 bootstrap 恢复此前运行时与其安装的默认属性。

具体 TestNG 回调存在测试方法与配置方法两种路径；不要把“继承 BaseTest”等同于自动安装全部企业能力。BaseTest 与 Listener 分工不同。

## 4. 重点一：数据驱动

### 4.1 数据驱动分成两种资产

`quality-assets/testcases` 是需求分析后的功能测试用例，便于评审与追溯；`src/test/resources` 中的套件 YAML/JSON5 是运行时测试数据。前者不是直接交给 DataDriveUtil 的格式。插件通过接口规格将需求用例转成运行时资产。

测试类负责“怎样测”，YAML 负责“有哪些场景”，JSON5 负责“每个场景传什么、期待什么”。这种拆分避免三条场景写三个几乎相同的方法，但不是把业务逻辑全部搬进 YAML。

### 4.2 文件定位规则

核心源码：`base-test-toolkit/src/main/java/io/testkit/basetest/data/DataDriveUtil.java`。

`loadTestData(method, suiteName)` 取方法所属类的包名，将点替换成斜线，再拼 `<suiteName>.yaml`。例如：

```text
测试包：demo.golden.framework.v3.http
套件名：golden_order_http_framework_v3
classpath资源：demo/golden/framework/v3/http/golden_order_http_framework_v3.yaml
源码位置：src/test/resources/demo/golden/framework/v3/http/同名.yaml
```

JSON5 路径相对于套件所在位置解析。移动测试类包名却不移动资源，会报 suite not found。另一个重载支持显式 Path，但跨机器使用绝对个人路径不利于 Git/CI 复现。

### 4.3 最小运行时 YAML

```yaml
testDataSuite:
  description: 创建订单
  cases:
    - name: 正常下单
      thought: 数量为1时可成功
      enabled: true
      users: []
      extraParams:
        sourceCaseId: ORDER-001
      request:
        - order_req.json5
      expect:
        - order_exp.json5
```

同目录 `order_req.json5`：

```json
{"sku":"SKU-DEMO","quantity":1}
```

`order_exp.json5`：

```json
{"status":201,"body":{"code":"OK","orderId":"ORDER-DEMO-001"}}
```

此 expected 的 status/body 外壳由当前 HTTP 测试方法解释；JsonDiff 本身不知道 HTTP 状态码。Dubbo 期望直接按实际测试类中的业务体结构维护，不要机械复制 HTTP status。

### 4.4 参数怎样绑定

当前生成方法的参数是：

```java
public void verifyApi(CaseContext context,
                      Map<String,Object> request,
                      Map<String,Object> expected)
```

解析器先拼 request 文件列表，再拼 expect 文件列表；遍历方法参数时，CaseContext 类型由元数据构造，不占 payload；其他参数依次消耗 payload，并按方法的泛型类型反序列化。

因此 1 个 request 文件 + 1 个 expect 文件对应上述 3 个参数。少文件、多文件均报错；不会自动按参数名搜索同名文件。复杂多入参需要明确文件顺序和方法签名，不能凭字段名称猜绑定关系。

### 4.5 CaseContext 与过滤

CaseContext 保存 name、thought、mockId、users、extraParams，构造时对集合做不可变拷贝。它不是全量业务请求对象，也不是自动建立依赖图的执行引擎。

- enabled=false：该 case 不进入 DataProvider 返回的数据行。
- testDataSuite.debugCases：非空时仅保留名称匹配的场景，匹配的是 case name。
- extraParams.sourceCaseId：用于需求用例追溯；不要把显示名当成永久唯一 ID。
- 系统属性 testkit.caseSuite：生成测试类读取它以覆盖套件名；套件仍应位于正确的类路径位置。
- YAML 的 environment 元数据不自动切换 ProjectSettings 的执行环境；环境选择依赖 test.env/TEST_ENV。

调试后要检查 debugCases 和 enabled，避免 CI 只跑了一条却以为全量通过。

### 4.6 类型和期望的正确性

ConfigLoader 选择 YAML/JSON/JSON5 解析器，payload 使用 StrictTypeModule。字段存在但类型错误应暴露，不要把所有数字都写成字符串后靠宽松转换掩盖契约错误。

需要测试“字符串数量”这类负例时，Map 可以保存字符串，但若方法参数是严格整数 DTO，可能在发送请求前就被解析器拒绝。此时使用适合保留非法输入的请求表示，不要把本地反序列化失败误当成服务端校验通过。

### 4.7 为什么放在公共能力层

YAML 定位、参数数量校验、类型转换是各业务通用机制；订单金额计算不是。若把数据解析复制进测试类，修复一次 JSON5 兼容问题就要改很多地方。若把所有业务前置都塞进解析器，加载数据就会触发外部副作用，失败定位和重试会更困难。

### 4.8 如何验证与替代方案

运行 DataDriveUtilTest；手动添加一条 YAML case，验证总数增加；把文件名写错，验证错误能指明路径；修改参数数量，验证在调用网络前失败；关闭一条验证过滤。

替代方案是把数据直接写在 DataProvider Java 中：类型提示好、适合复杂构造，但非开发人员评审成本高、需求资产追溯难。Excel 可读但合并冲突和类型歧义更大。当前 YAML/JSON5 适合 Git，代价是需要保持包路径、文件引用和签名一致。

## 5. 重点二：身份管理

### 5.1 四个对象分别负责什么

| 对象 | 职责 | 不负责 |
| --- | --- | --- |
| UserIdentity | alias、subject、accessToken、attributes | 自动调用登录接口、Token刷新 |
| IdentityProvider | acquire(profile)、release(identity) | 自动识别业务应使用哪个角色 |
| IdentityContext | 当前线程的嵌套身份作用域 | 跨进程共享账号锁 |
| UseIdentity | 测试方法或类上声明角色 profile | 把该角色变成真实平台账号 |

profile 是角色/账号池名称，例如 buyer、reviewer；alias 是某个身份实例的稳定别名。多个 profile 若共享同一账号，应使用一致 alias，避免同一实际账号被不同别名重复租用。

### 5.2 自动获取规则

PortableTestNgListener 在测试方法执行前读取：方法上的 UseIdentity 优先；没有再看类上的 UseIdentity；仍没有则读取 CaseContext.users。

单个 YAML user 可以自动选作 profile；多个 users 且没有显式 UseIdentity 会报错。框架不会偷偷从多个角色中任选一个，也不会因为写了三个 users 就自动执行三遍。

确定 profile 后，调用当前 runtime.identities().acquire，绑定 IdentityContext；收尾关闭作用域并 release。必须启用 Listener 且装配真实 provider，只有 BaseTest 不足以完成这个流程。

### 5.3 本地账号池接入示例

以下是需要你在测试工程增加的示例，不是当前无鉴权订单服务的现有配置：

```java
var buyer = new UserIdentity("buyer-local-1", "user-1001", "local-demo-token", Map.of());
var identities = new InMemoryIdentityProvider(Map.of("buyer", List.of(buyer)));
var report = new JsonLinesResultPublisher(Path.of("target/identity-demo.jsonl"));
var runtime = new AutomationRuntime(identities, null, report, null,
    report, null, null, null);
```

在项目 bootstrap 的既有 runtime 装配处替换 identities；不要为每个测试方法安装一份全局 runtime。上面未列 imports，按实际类导入；示例 Token 仅为本地演示，不应替换为 Git 中的真实凭证。

测试类或方法添加：

```java
@UseIdentity("buyer")
```

也可在单个 YAML case 设置 `users: [buyer]`。二者同时存在时以注解为准，不要期望 YAML 覆盖方法注解。

### 5.4 获取身份不等于所有调用自动认证

ApiClient.authenticated 会从 IdentityContext 读取 accessToken 并设置 Bearer Authorization；普通 request 不自动加认证。

当前生成的订单 HTTP API 调用的是 request，且本地订单服务无鉴权。因此给 YAML 加 users，并不能证明业务请求已经携带 Token。接入真实鉴权时需要明确 API 使用 authenticated 或按公司协议设置 Header。

Dubbo 的认证一般通过 attachments 或公司上下文传递，不能照搬 HTTP Header。应在项目 RPC 封装中把允许的身份信息映射为真实协议附件，并验证服务端确实识别。

### 5.5 手工作用域及释放

```java
UserIdentity identity = identities.acquire("buyer");
try (IdentityContext scope = IdentityContext.use(identity)) {
    UserIdentity active = IdentityContext.requireCurrent();
    // 此处调用显式使用当前身份的业务API。
} finally {
    identities.release(identity);
}
```

IdentityContext.close 只恢复当前线程上下文，不自动调用 provider.release；Listener 自动流程会分别完成两件事。手工流程忘记 release 会耗尽池；只 release 不 close 会在线程池复用时串身份。

作用域必须在创建线程按后进先出关闭；内层 buyer 切 reviewer 后，内层关闭应恢复 buyer。不能把 scope 传到另一个线程 close。

### 5.6 并发与跨进程边界

InMemoryIdentityProvider 用 ConcurrentHashMap.putIfAbsent 按 alias 租用，单实例内不会同时租同一 alias；没有可用账号立即失败，不会无限等待。多个独立 provider 实例或多个 JVM 不共享这个锁。

IdentityContext 使用 ThreadLocal 栈，隔离同一 JVM 不同线程；新建异步线程不会天然继承身份。并发测试必须考虑账号池容量、异步上下文显式传递和共享账号业务状态。

100 人团队或 CI 多节点共享账号，需要企业账号平台/数据库租约等跨进程协调、过期回收、Token 刷新和审计；不能声称内存池已解决分布式账号争抢。

### 5.7 真实账号平台适配步骤

1. 实现 IdentityProvider；profile 映射业务角色与环境。
2. acquire 从受控平台租账号并获取/刷新 Token，设置超时与失败策略。
3. 返回 UserIdentity，不在 toString、日志或用例文件暴露凭证。
4. release 归还租约；对进程崩溃提供平台 TTL 回收，不仅依赖 finally。
5. 在 ProjectBootstrap 装配 provider，协议封装显式读取身份。
6. 用缺角色、池耗尽、Token过期、并发租用、服务异常与归还失败测试适配器。

UserIdentity.toString 隐藏 Token，但 attributes 以及业务自行打印不自动成为安全区。日志脱敏也不能代替密钥管理。

### 5.8 为何独立成层、替代方案

如果每个用例自己登录，重复逻辑多、Token刷新规则分散、失败后很难统一归还。若把登录写死进 HTTP 客户端，Dubbo/SDK 无法复用且协议层绑死公司平台。

独立 provider + context 的代价是需要显式装配、管理生命周期和协议映射；收益是换账号平台不改所有用例。全局 static Token 简单但会串账号并掩盖权限场景，只适合明确单用户短演示，不适合并发回归。

## 6. 数据准备、造数与清理

### 6.1 四个同名相关概念不能混淆

- JSON5 请求数据：静态测试输入，不是已经在服务中存在的订单/库存。
- 插件生成的 XxxDataBuilder 类：业务扩展点，当前默认复制 Map、cleanup 留 TODO。
- 框架 DataFactory 接口：统一 prepare(DataPreparationRequest) 的接入能力，默认 unsupported。
- 框架 `@DataBuilder` 注解及 DataBuilderProcessor：编译期生成 TestNG 适配类的机制，不等于上述普通业务类自动完成造数。

注解处理器对方法有 public、非 static、非 final 等要求，生成 `_DataBuilderAdapter`。是否启用还要看项目编译器和注解处理配置；不能仅命名为 DataBuilder 就期待编译器生成代码。

### 6.2 接入真实造数的流程

1. 定义场景，例如 prepareOrderStock，明确输入 SKU、数量、环境和身份。
2. 实现 DataFactory，调用造数平台或批准的测试 API；返回真实 ID 和清理所需标识。
3. 在 runtime 装配实现，业务 DataBuilder.prepare 调用它，并只补充应动态生成的字段。
4. 保留显式非法输入，quantity=0 不能被“自动补全”改成 1。
5. 返回本次创建资源的所有权标识；登记清理动作，只删除本次生成的数据。
6. 造数失败应在真实业务调用前清晰失败，不构造虚假 ID 继续通过。
7. 清理具备幂等、有限超时，并记录失败；需要崩溃恢复时设计 TTL/补偿任务。

### 6.3 BaseTest 与清理栈

`deferCleanup` 注册 AutoCloseable 动作，BaseTest.AfterMethod(alwaysRun=true) 调用 CleanupStack.close，finally 移除其线程局部清理栈、CaseContext、ReturnValueContext。

当前生成测试的模式是 prepare 成功后立即登记 cleanup，再调用接口和断言。因此断言失败仍可清理；但 prepare 在返回前已创建部分资源再抛异常时，尚未来得及登记外层清理，prepare 自己必须有补偿。不能把所有失败路径都寄托在后续 deferCleanup。

不要在共享可变字段里保存“最后创建的订单”供并发用例清理。将当前调用资源保存在局部变量、调用上下文或有所有权的租约对象中。

### 6.4 ReturnValueContext

线程局部 Map，用 put/get/snapshot 在同一线程当前调用中传递前置结果；BaseTest 收尾会 clear。它不是跨用例依赖仓库，更不是跨进程数据库。测试 B 依赖测试 A 曾在线程里写入的 ID，不是可靠方案。

### 6.5 验证与代价

验证正常、业务失败、断言失败、prepare 部分失败、cleanup 抛异常、重复 cleanup 和并发两条创建。断言必须能确认“自己的资源被清掉，其他用例的数据仍保留”。

全部预置静态数据更快但易被其他测试污染；每次动态造数隔离更好但慢、依赖平台。可以分层组合：静态字典 + 每次独立业务资源，避免每条用例都重建整个环境。

## 7. 配置与环境管理

框架的 ConfigLoader/TestEnvironment 是通用配置能力；初始化器生成的 ProjectSettings 是项目的环境文件加载器，二者不是同一个类。

当前 ProjectSettings 先取系统属性 test.env，再取 TEST_ENV，默认 local；加载 classpath 下 environments/<env>.properties，仅为尚未设置的系统属性填默认值。已有 -D 属性优先。执行结束只清理由它安装且值未改变的默认属性。

因此：配置写在 src/main/resources，不要只改 target/classes；切环境会读另一份文件；IDEA 的旧 VM options 可能覆盖文件；环境配置不在类路径会启动失败。Properties 加载使用 Java Properties 的语义，含中文/特殊转义应按实际编码行为测试，不把敏感值直接写文件。

为何不写死地址：同一测试代码要可复用于 local/test/pre。为何仍保留 -D：CI 临时覆盖便利。代价是来源优先级必须清楚，排查时要核对实际执行环境和 VM options。

## 8. 运行时装配与生命周期

AutomationRuntime 包含 identities、mocks、results、coverage、invocationLogs、jobs、discovery、dataFactory。它是能力集合，不是后端服务，也不会替你启动注册中心。

默认值非常重要：身份未配置时 acquire 抛 unsupported；DataFactory 和 jobs 默认 unsupported；discovery 默认空；coverage/logsink 可为 noop；results 默认内存收集。这些默认值帮助本地最小运行，但不等于企业平台已连接。

RuntimeRegistry 管理当前装配和作用域；ProjectBootstrap 是业务工程的装配根。类并行需要不同 runtime 时优先理解 RuntimeProvider，避免每个类在 BeforeClass/AfterClass 随意 install/reset 全局值造成串扰。Listener 为每次调用捕获 runtime，并在其收尾时使用捕获值，而不是清理时重新猜当前全局 provider。

BaseTest 负责用例与业务清理；Listener 负责运行范围、身份、Mock、结果；bootstrap 负责整个执行的装配与恢复。把全部职责堆进 BaseTest 会让基类越来越难维护，也让不继承基类的测试难以接入。

验证入口：BaseTestTest、AutomationRuntimeTest、RuntimeIsolationTest、LifecycleRegressionTest、LifecycleClosureTest。重点看失败回调和配置失败，不仅正常路径。

## 9. 协议调用层

### 9.1 HTTP

业务 API 类决定方法、路径和业务头；ApiClient 决定 URI 合法性、JSON 编码、超时、请求执行和日志。

默认超时 10 秒；不自动跟随重定向；base URL 不接受内嵌凭证/查询/fragment，路径不能绕去其他服务器。以 `/` 开头的路径按 URI 规则从站点根解析，不要假设会保留 base URL 中业务前缀。

HTTP 400/500 可以是有效响应，不一定抛传输异常。业务测试要断言状态和响应体；网络异常与业务错误码不是一回事。ApiResponse.status/json 供测试断言，协议层不应强行认定所有非200都失败。

### 9.2 Dubbo

DubboClient 使用接口名、group/version、注册中心或 directUrl、超时，调用时传方法名、Java 参数类型数组、参数对象数组和 attachments。

本地：接口 demo.golden.OrderService，create，参数类型 java.util.Map，参数是一个 Map，地址 dubbo://[::1]:20891。参数类型描述和业务 JSON 字段不同；写错签名会在 RPC 解析/匹配阶段失败。

Dubbo 响应是对象而不是 HTTP ApiResponse；没有通用 HTTP201/400。客户端引用需要 close；生成测试在 AfterClass 关闭 API。直连方便无注册中心演练，但不能证明注册中心发现/路由已验证。

### 9.3 SDK、数据库、任务与消息

SdkInvoker 提供包装入口，具体 SDK 初始化、鉴权与关闭仍由项目实现。JdbcSession 用于数据库交互与验证，需独立测试库和受限权限；不要把测试 SQL 当生产数据修复。

job/discovery 与 Kafka/XXL-JOB 适配为异步流程提供接入口。消息已发送或任务已触发不等于业务状态正确；需有相关 ID、有限等待与最终业务断言。未配置/未启动真实平台的本地测试不能当公司环境验收。

为何分适配层：外部 SDK/中间件版本变化频繁，通用层不应绑定每个平台。代价是适配器有自己的依赖、契约与集成测试责任。

## 10. 断言层

JsonDiff.strict 返回差异列表，额外字段、缺失、类型与值差异均可能产生差异；它本身不直接让 TestNG 失败，需要 Assert.assertTrue(differences.isEmpty(), ...)。

lenient 允许实际结果额外字段，但不代表类型和值随意。动态 traceId/time 可用 ignoredPaths 控制；忽略规则越广越容易漏测，不要为让测试变绿忽略整个 body。

JsonContract 用于契约检查；Await 用于有界条件等待。异步场景优先轮询明确条件并设置总超时，避免固定 sleep 太短不稳定、太长拖慢回归。等待中观察的条件不应反复触发具有副作用的下单操作。

具体比较策略属于测试意图；协议客户端不应内置所有订单断言。验证入口看 JsonContractTest 和 assertion 相关测试，同时用 DataDriveUtilTest 理解类型输入的前置约束。

## 11. 日志、结果、追踪三件事

| 产物 | 回答的问题 | 典型入口 |
| --- | --- | --- |
| 调用诊断日志 | 实际发了什么、收了什么、耗时及异常位置 | ProtocolCallLog，target/logs |
| 测试结果 | 哪条用例通过/失败/跳过，配置是否失败 | TestNG/Surefire、JsonLinesResultPublisher |
| 追溯标识 | 同一次运行、用例调用和接口请求如何关联 | TraceContext、runId/caseId/callId、sourceCaseId |

请求收到200只说明通信结果，不说明断言通过；出现 RESPONSE 日志也可能随后断言失败。sourceCaseId 是需求用例ID，调用级 caseId 还承担区分具体执行实例的作用，不要混为永久业务主键。

HTTP/Dubbo 已自动记录 REQUEST + RESPONSE/ERROR，按 callId 配对。控制台前缀 `[TESTKIT CALL]`，文件是无前缀 JSONL。正文默认关闭，初始化器 local/test 显式打开脱敏正文，pre 关闭。

```properties
testkit.log.enabled=true
testkit.log.console=true
testkit.log.bodies=true
testkit.log.file=target/logs/api-calls-${pid}.jsonl
testkit.log.maxBodyChars=4096
testkit.log.maxFileBytes=10485760
testkit.log.redactKeys=businessPrivateField
```

ProtocolCallLog 递归脱敏、截断并轮转；默认按 PID 隔离避免多个 JVM 争写。诊断写盘/序列化失败会安全告警，不改变真实传输结果，但不能据此声称所有显式 InvocationLogSink 错误都被吞掉，既有指标 sink 保持自身语义。

正文脱敏不保证识别所有业务秘密；自定义隐私字段仍需配置，日志保留/访问控制由项目与 CI 管理。SDK 目前不能笼统声称自动采集全部入参出参。详见框架 PROTOCOL-LOGGING.md。

验证：正常调用、超时、拒绝连接、敏感头/嵌套字段、超长正文、磁盘失败与并发。必须能从日志找到实际 target 和参数，但不能找到真实凭证。

## 12. Mock、服务发现和并发资源

MockEngine/MockSession 负责打开与关闭场景。YAML mockId 会触发 Listener 打开场景，但默认 InMemoryMockEngine 不是公司流量代理；没有规则和网络接入时，不能声称后端外部依赖已被替换。真实 HTTP Mock 和企业代理要分别验证。

ServiceDiscovery 表示执行时寻找服务实例；StaticServiceDiscovery 是显式静态配置。它与插件按接口路径“发现源代码 BO/VO/调用链”的 SPI 不是同一种发现，不能混淆。

ResourceLeaseProvider/JdbcResourceLeaseProvider 提供资源租约能力，解决共享资源归属问题；是否满足多节点、数据库方言、过期回收和故障恢复取决于实际部署验证。ThreadLocal 不能代替数据库租约。

企业模式可管理团队归属、执行计划、分片与目标策略。它是协作/执行治理，不是“启动100线程就支持100人团队”。多人接入还需要版本发布、权限、环境隔离、账号和造数容量、评审与CI门禁。

## 13. 修改需求该去哪里

| 要修改的内容 | 应修改位置 | 不建议的位置 |
| --- | --- | --- |
| 接口路径或订单字段 | 业务API、规格、测试数据 | ApiClient 通用实现 |
| 增加边界场景 | 需求用例及运行时 YAML/JSON5 | 复制整个测试类 |
| 切环境地址 | 当前项目环境配置 | 每个测试写死URL |
| 接公司账号平台 | IdentityProvider实现 + bootstrap + 协议认证映射 | YAML写真实Token |
| 接公司造数平台 | DataFactory实现 + 业务DataBuilder | 修改JSON解析器调用平台 |
| 改全局调用日志 | 框架 ProtocolCallLog/协议接入 | 每个测试println |
| 加新中间件 | 独立适配器与契约测试 | 在BaseTest堆客户端 |
| 修改生成模板 | 初始化器或脚手架生成器，对应职责 | 手改框架业务包 |

## 14. 面向设计理解的自检

对每个模块至少能回答五件事：解决什么失败、为什么放在这一层、如何验证、替代方案是什么、采用它的代价是什么。

以数据驱动为例：解决场景复制与类型混乱；放通用层使所有业务复用解析规则；通过路径/签名/过滤/异常测试验证；替代是Java数据提供器；代价是资源引用和签名必须一致。

以身份为例：解决权限场景与并发账号串用；独立provider避免协议层绑定公司平台；验证隔离/租用/释放/异常；替代是每次登录或单静态Token；代价是接入平台、租约与Token生命周期需要治理。

以日志为例：解决用例失败没有请求响应证据；放协议层统一拦截；验证正常/异常/脱敏/落盘；替代是业务手写或外部代理；代价是性能、隐私、存储和保留策略。不要只说“用了TestNG和ThreadLocal”，要说清失败路径和边界。
