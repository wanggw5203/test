# 三个工程完整操作手册

## 1. 总体工作顺序

框架构建并提供依赖 → 初始化器创建自动化工程 → IDEA 打开该工程 → 插件登记需求、生成 TAD/用例/接口脚手架 → 配置环境并启动被测服务 → Maven/TestNG 执行 → 检查报告与日志 → 将审核后的资产纳入 Git。

这里的“工程初始化”与“业务脚手架生成”不同：前者创建 POM、公共启动与环境文件；后者在现有工程添加接口 API、业务数据扩展、测试类和测试数据。不要用接口生成来修复 Maven 依赖，也不要重复初始化一个已经存在的 Maven 工程。

## 2. 环境准备

在 PowerShell 执行：

```powershell
cd E:\AITest\test
java -version
mvn -version
git --version
```

本套演练统一使用 JDK 21、Maven 3.9+。框架 Java 编译基线 17，初始化器本身可用 17，生成工程和插件开发使用 21。IDEA 的 Project SDK、Maven Runner JRE 也选 21；终端正常不代表 IDEA 配置相同。

首次构建需要下载依赖，联网和 Maven 私服设置应由本机环境准备；工程不包含公司账号与虚构私服地址。不要把 Token 写进 Git 配置文件。

## 3. 工程一：自动化框架

### 3.1 在 IDEA 中打开哪个目录

1. File → Open → 选择 `E:\AITest\test\baseTest\pom.xml`。
2. 按 Maven 工程导入，SDK 选 21。
3. 等待 Maven 同步，确认能看到 base-test-toolkit、enterprise-adapters、父 POM/BOM、示例等模块。
4. 学习时从 base-test-toolkit 进入，不要从所有历史 class 逐个阅读。

### 3.2 先构建框架并安装到本机仓库

```powershell
cd E:\AITest\test
mvn -B -ntp -f baseTest/pom.xml -pl base-test-toolkit,enterprise-adapters -am install
```

成功标准：BUILD SUCCESS，并在本机 Maven 仓库安装当前 `1.1.0-SNAPSHOT`。自动化项目解析的是 Maven 依赖，不会因为你改了框架源码就自动使用新实现；修改后应重新 install，然后刷新业务工程 Maven。

本命令验证所选模块及上游，不等于执行了全部企业环境验收。若只为开发时快速编译，可以加 `-DskipTests`，但这不算测试通过证据。

需要框架整体生命周期、SBOM 和门禁验证时，使用框架 README 的完整入口；需 PowerShell 7.2+：

```powershell
cd E:\AITest\test\baseTest
pwsh -NoProfile -File .\verify-lifecycle.ps1
```

此完整入口的报告与所选模块 install 的范围不同，不要混报结果。任何会触达真实 Kafka、任务平台的 live profile，都要先确认独立测试环境及权限。

### 3.3 框架怎么被业务项目引入

查看生成工程 POM：核心依赖是 `io.testkit:base-test-toolkit:1.1.0-SNAPSHOT`；Dubbo 工程还引入 enterprise-adapters 和所需协议依赖。需要 main 源码引用的类必须在编译类路径上，不能把所有框架依赖都改成 test scope。

职责归属：公共协议、数据解析、身份抽象、生命周期、报告放框架；订单路径、公司账号平台、造数规则等放业务项目或企业适配层。改业务路径不应重新发布公共框架。

### 3.4 如何单独学习或验证一个模块

1. 在 IDEA 打开对应 `src/test/java` 的测试类。
2. 运行测试类，先读输入和断言，再读实现。
3. 数据驱动看 DataDriveUtilTest；身份看 IdentityContextTest；运行时看 RuntimeIsolationTest、LifecycleRegressionTest；日志看 ProtocolCallLogTest。
4. 用测试类定位实际能力，不要仅根据文档中的能力名称判断已接入公司平台。

详细模块说明见 [框架分层模块详解](自动化框架分层模块详解.md)。

## 4. 工程二：自动化项目初始化器

### 4.1 从源码构建

```powershell
cd E:\AITest\test
mvn -B -ntp -f tools/automation-project-initializer/pom.xml clean package
```

成功后 JAR 位于 `tools/automation-project-initializer/target/automation-project-initializer.jar`。仓库现有分发包为 `dist/automation-project-initializer-1.0.1.jar`；重新构建后的最新结果应从 target 使用，不能默认旧 dist 包也自动更新了。

### 4.2 创建 HTTP 自动化项目

下列路径仅为新工程示例；已存在时换一个新目录，不要强制覆盖：

```powershell
cd E:\AITest\test
java -jar tools/automation-project-initializer/target/automation-project-initializer.jar --type HTTP --directory E:/AITest/learning-http-tests --artifact-id learning-http-tests --group-id com.example --package com.example.automation.http --framework-version 1.1.0-SNAPSHOT
```

参数含义：type 决定模板；directory 决定磁盘位置；group-id/artifact-id 是 Maven 坐标；package 是基础 Java 包；framework-version 是需要解析的框架版本。

### 4.3 创建 Dubbo 或 SDK 工程

沿用上面的命令，将 type 改为 DUBBO 或 SDK，同时修改 directory、artifact-id、package，避免混用同一目录。

Dubbo 模板包含 RPC 基础封装与依赖；SDK 模板只有适配扩展入口，还需自己提供真实 SDK 坐标、客户端、鉴权和释放实现。SDK 初始化成功不等于 SDK 方法用例已自动生成。

### 4.4 打开并验证新工程

1. IDEA → File → Open，选择新工程的 pom.xml。
2. 导入 Maven，Project SDK 与 Maven Runner 选 21。
3. 查看 `src/main/java/<基础包>/bootstrap/ProjectBootstrap.java`。
4. 查看 `config/ProjectSettings.java` 和 `src/main/resources/environments/local.properties`。
5. 查看 `src/main/resources/META-INF/services/org.testng.ITestNGListener`，确认注册项目启动监听器。
6. 在新工程根目录执行 `mvn -B -ntp test`。
7. 预期初始化冒烟通过，并生成报告；此时没有真实业务用例，所以还不能判断 HTTP/Dubbo 联通。

### 4.5 目录怎么使用

| 路径 | 放什么 | 日常由谁修改 |
| --- | --- | --- |
| pom.xml | 依赖、构建、测试插件 | 项目维护者；不由业务接口生成反复改写 |
| src/main/java/.../bootstrap | 项目能力装配和执行入口 | 自动化项目维护者 |
| src/main/java/.../config | 环境文件加载 | 自动化项目维护者 |
| src/main/java/.../api | 可复用协议/业务调用 | 开发者或插件 |
| src/main/java/.../data | 业务造数、清理扩展 | 开发者或插件 |
| src/main/resources/environments | local/test/pre 配置 | 项目维护者，不提交密钥 |
| src/test/java | TestNG 测试与断言编排 | 开发者或插件 |
| src/test/resources | YAML 套件和 JSON/JSON5 入参、期望 | 开发者或插件 |
| .ai-test-flow/automation-project.yaml | 工程类型与生成约定 | 初始化器生成，评审维护 |
| quality-assets | 需求、分析、功能用例、证据 | 使用插件并经人工评审 |

初始化器拒绝已有 Maven/Gradle 工程及文件冲突，这是保护机制。已有工程接入应按项目约定评审改造，而非删除旧 POM 再初始化。

## 5. 工程三：IDEA 插件

### 5.1 构建、测试与安装

```powershell
cd E:\AITest\test\tools\ai-test-flow-idea-plugin
.\gradlew.bat test buildPlugin --no-configuration-cache
```

测试成功后，从 `build/distributions/` 取此次新 ZIP。当前已分发版本是 `E:\AITest\test\dist\ai-test-flow-idea-plugin-1.6.1.zip`。不要同时并发启动两个写相同 build/test-results 的测试命令，否则 Windows 可能出现文件占用。

安装步骤：IDEA → Settings → Plugins → 齿轮 → Install Plugin from Disk → 选择 ZIP → 重启 IDEA → 打开自动化项目 → 打开 AI Test Flow 工具窗口。插件的 Java/IDE 平台基线受当前构建配置约束；不兼容时先看安装提示，不要反复安装旧包。

需要调试插件源码时在该工程执行 `gradlew.bat runIde`，它启动开发沙箱 IDEA；沙箱与日常 IDEA 的插件设置不是同一份。普通用户只需安装 ZIP，不必运行插件源码工程。

### 5.2 也可以从插件创建自动化工程

1. 打开“流程与配置”。
2. 点击“创建自动化项目（HTTP / Dubbo / SDK）”。
3. 填类型、目标绝对目录、Maven 坐标、包名和框架版本。
4. 点击“生成项目”。
5. 再用 File → Open 打开新目录并导入 Maven。

这是插件调用独立初始化器，不代表初始化规则全部写进接口生成器。生成后不自动替你切换当前 IDEA 工程。

### 5.3 第一次验证模型流程：使用黄金集

1. 确认当前打开的是目标自动化工程，不是框架工程或插件源码工程。
2. 点击“初始化企业工作区”，检查 `.ai-test-flow/workspace.json` 和资产目录。
3. 先选择 HTTP 或 DUBBO 协议。
4. 点击“载入黄金集 Demo”。它会重新载入示例输入，因此应在自行修改 PRD 之前使用。
5. HTTP 目标填写 `POST /demo/orders`；Dubbo 目标使用 `demo.golden.OrderService#create(java.util.Map)`。
6. 检查输入、证据和生成目标，按下文分步执行。熟悉后再用“运行完整链路（全部资产）”。

黄金集无须模型 Key，不访问远程模型，但始终返回同一组订单样例。用另一份 PRD 得到同样内容是黄金集行为，不是模型真正分析了新需求。

### 5.4 登记真实需求输入

1. 将 Markdown 需求放到项目中，或在插件选择 Word/PDF/HTML 等输入。
2. 项目外输入会登记到 quality-assets/inputs，保留可追溯来源；不能只留个人桌面路径。
3. 手工输入或编辑器选区也应先固化为项目内输入资产。
4. 原型截图能作为证据，但不能把截图当成完整的 API 字段契约；字段、类型、异常与权限需要补齐。
5. 接口、代码、执行日志等证据登记到 quality-assets/evidence。
6. 确认需求 assetId 与目标位置，避免把另一需求的输出接到本次流程。

若启用 Markdown 原位更新，要先保留 Git 版本并审查差异；保留原始 PRD 与另存 TAD 更便于初学者对照。插件写回项目不等于自动提交 Git。

### 5.5 分阶段生成与验收

| 阶段 | 操作 | 必看产物 | 本阶段确认点 |
| --- | --- | --- | --- |
| 需求分析 | 生成结构化 TAD | quality-assets/analysis | 规则、边界、异常、风险、待澄清项是否与需求一致 |
| 功能用例 | 从 TAD 生成测试用例 | quality-assets/testcases | caseId 唯一，规则追溯完整，正反边界都有 |
| 接口自动化 | 选择接口，生成接口规格及脚手架 | quality-assets/automation、main/test | HTTP/Dubbo 类型、方法、字段、上游 caseId、环境数据正确 |
| 页面资产 | 按需要生成 Web ATC | quality-assets/automation | 定位器、页面证据经确认；无页面时不算已执行 |
| 反馈 | 输入真实执行证据后生成反馈 | feedback、manifest、run record | 明确 passed/failed/blocked，不伪造执行状态 |

界面中的阶段序号以实际按钮为准，业务依赖关系是 PRD → TAD → 用例 → 接口规格 → 代码/数据 → 外部执行 → 证据反馈。

### 5.6 接口生成后的文件

HTTP 黄金集使用包 `demo.golden.framework.v3.http`，Dubbo 使用 `.dubbo`：

- main 下的 `GoldenOrderHttpTestApi` 或 `GoldenOrderDubboTestApi`：调用接口。
- main 下的 `...DataBuilder`：准备和清理的业务扩展点；当前默认复制输入，不代表造数平台已接入。
- test 下的 `GoldenOrderHttpTest` 或 `GoldenOrderDubboTest`：BaseTest、DataProvider、调用与断言。
- test/resources 对应包目录：一份套件 YAML，三份请求 JSON5、三份期望 JSON5。
- `.api-test-generator/<apiCode>/`：生成清单、加工计划、接口 testng.xml。
- `.ai-test-flow/manifests` 与 runs：来源、摘要、执行阶段追溯。

HTTP apiCode 为 golden_order_http_framework_v3；Dubbo 为 golden_order_dubbo_framework_v3。生成后先阅读并编译，不要只看“生成成功”。

### 5.7 覆盖保护失败怎么办

1. 看运行日志：是质量门禁、项目依赖缺失，还是已有文件摘要不一致。
2. 查看 Git diff，确认已有文件是否被你修改。
3. 门禁拒绝的候选内容查看 `.ai-test-flow/rejected`，修正输入或规则后再生成。
4. 已有人工代码要保留；使用新的接口版本/输出约定或干净练习项目。
5. 不要删除 manifest 来绕过保护，更不要让模型强制覆盖所有 Java。

### 5.8 切换真实模型

Settings → Tools → AI Test Flow → 关闭黄金集 Demo → 填企业模型网关、模型、Key → 保存 → 用小需求逐阶段验证。

Key 保存在 IDEA Password Safe；不要放 PRD、YAML、截图和 Git。内置 Skills 随插件发布，用户不需要在个人目录准备一份 Skill 文件。真实网关调用入口保留，但当前本地演练不构成远程模型质量验证；先评审 TAD/用例，再生成代码。

接口发现目前保留 SPI 和手工证据通道；真实 PSI/UAST、OpenAPI、Dubbo 元数据抓取还需 Provider。输入接口路径不代表当前一定能自动扫描完整业务调用链或取得所有 BO/VO。

## 6. 三个工程串起来：本地 HTTP/Dubbo

### 6.1 启动被测服务

```powershell
cd E:\AITest\test\validation\local-http-dubbo-flow-20261018
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Start-LocalService.ps1
Invoke-RestMethod http://127.0.0.1:18081/health
```

也可双击 start-service.cmd。一个进程同时启动 HTTP18081、Dubbo20891。没有注册中心。不要再在 IDEA 重复启动同一个服务，否则端口冲突。

### 6.2 配置自动化项目，而非服务源码

打开各自自动化工程 `src/main/resources/environments/local.properties`：

```properties
api.baseUrl=http://127.0.0.1:18081/
dubbo.directUrl=dubbo://[::1]:20891
testkit.log.enabled=true
testkit.log.console=true
testkit.log.bodies=true
testkit.log.file=target/logs/api-calls-${pid}.jsonl
```

模板中可能还有 registry 配置，保持本地无注册中心设置。Dubbo 生成 API 实际读取 `dubbo.registry` 和 `dubbo.directUrl`；不要仅加一个近似拼写的键就认为客户端生效。直连演练以 directUrl 为准，具体配置映射查看生成 API 和 bootstrap。

选择 local 时不用额外地址启动参数。`-Dtest.env=test` 会切换到另一份环境文件；因此只改 local 却运行 test 环境不会生效。系统属性优先于文件默认值。

### 6.3 执行真实业务测试

在 HTTP 工程根目录执行：

```powershell
mvn -B -ntp test
```

在 Dubbo 工程根目录执行同一命令。或在 IDEA 分别运行 GoldenOrderHttpTest、GoldenOrderDubboTest。

本地黄金集完整模块预期 4 条：初始化冒烟 1 条，加业务 3 条。单独业务类是 3 条。默认初始化 testng.xml 按基础包扫描，可能只跑冒烟，不能拿 1 条成功当接口验证。使用明确业务类或 `.api-test-generator/<apiCode>/testng.xml`。

### 6.4 验收与日志

1. 看 Surefire 总数，不只看退出码。
2. 看 `[TESTKIT CALL]` 或 target/logs 中实际请求、响应、耗时。
3. 看 target 下结构化报告与 target/surefire-reports。
4. Dubbo 核对 interface、method、parameterTypes、directUrl；health 成功不等于 RPC 成功。
5. 看服务 runtime/service-requests.jsonl 的 DUBBO 记录，确认本轮真实服务收到了调用。
6. 失败按“配置加载 → 网络 → 协议 → 数据 → 断言 → 清理”顺序查。

### 6.5 从零自动复验，不覆盖你的修改

```powershell
cd E:\AITest\test\validation\local-http-dubbo-flow-20261018
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Verify-FullFlow.ps1 -Fresh -ConfigOnly
```

Fresh 在 rechecks 新建两个工程；ConfigOnly 用环境文件设置地址。它会运行生成链路、真实 HTTP/RPC、故障注入与恢复。详细手动过程、结果和证据见本目录索引链接。

## 7. Git 评审与团队协作

先检查 git status 与 git diff，再由团队决定提交。建议纳管：POM、main/test、PRD/TAD、功能用例、接口规格、生成清单、已脱敏审核的证据。忽略 target、runtime、本机 IDEA 文件、密钥和未经审核的日志。

插件不会替你 commit/push，也没有把 Git 强制绑定到 GitHub。公司 GitLab、私有 Git、其他远程仓库都可以。关键是输入与产物在项目中形成可评审版本，而非保存在个人机器隐藏目录。

## 8. 完成标准

- 框架依赖可解析，修改后知道如何 install 和让业务工程更新。
- 能用初始化器创建 HTTP/Dubbo 工程，并解释各目录作用。
- 能在插件中找到输入、TAD、功能用例、接口规格、Java、测试数据及追溯清单。
- 明白黄金集和真实模型的区别，不把固定响应当需求分析准确性。
- 服务已启动，真实 HTTP 和 RPC 业务用例都执行，有入参出参及断言证据。
- 故障能被检测、恢复后能通过；资产修改可通过 Git 审查。
- 明确剩余边界：真实模型语义质量、公司接口发现 Provider、真实造数/账号平台和远程环境需要独立接入与验收。
